# 第六阶段：审计追踪闭环设计说明

## 背景与目标

本阶段仅修改 `frontend`，接入真实审计列表、详情、单条完整性校验、全局链摘要和导出接口，形成“列表—详情—解释链—校验—导出—关联轮次”的只读闭环。业务结论、评分、哈希状态、时间线和执行结果完全以后端响应为准。

## 现状与约束

- 冻结列表接口仅支持 `page`、`page_size`、`decision`、`start_time`、`end_time`。
- `AuditListResponse` 只提供 `items`、`total`、`page`、`page_size`，总页数由前端推导。
- 列表项的 `final_decision` 是结构化裁决对象；现有前端类型需要修正。
- 列表项不包含逐条审计链状态、输入类型或授权详情，不为这些字段伪造值，也不触发逐行校验请求。
- 详情响应包含语义、证据摘要、评分、安全门、复核、授权、执行、`workflow_events` 和链状态。
- 单条校验返回记录哈希、前序链接、审计链、工作流链和复核终态关联校验结果。
- 全局链接口仅返回 `{ valid }`；最近校验时间记录为前端请求完成时间并明确标注。
- 导出接口当前返回后端已脱敏 JSON；前端仍递归删除名称包含 `token`、`authorization_token` 或 `secret` 的字段。

## 方案对比

### 方案一：双页面控制器与专用数据钩子

- 优点：列表与详情状态完全隔离；请求取消、局部错误和刷新边界清晰；延续现有页面架构。
- 缺点：文件数量略多。

### 方案二：单一审计控制器

- 优点：表面文件数量少。
- 缺点：列表筛选、详情、校验和导出状态耦合，路由切换时更容易残留旧状态。

### 方案三：React Router 数据加载器

- 优点：路由数据与地址天然绑定。
- 缺点：需要重构现有路由体系，保留旧列表、局部刷新和按需导出处理复杂，超出本阶段范围。

## 推荐方案

采用方案一。`useAuditListController` 与 `useAuditDetailController` 完全独立；控制器只协调专用钩子，专用钩子之间不得互相导入。

## 详细设计

### 架构与依赖

依赖方向固定为：页面 → 控制器 → 专用钩子 → API；控制器或组件 → 工具函数 → 契约类型。API、工具、组件和专用钩子均不反向导入页面或控制器，因此不存在循环依赖。

审计列表页和详情页均从 `App` 独立懒加载；审计页面不静态引用二维或三维图谱渲染器。

### 状态归属

- 地址栏：列表的页码、每页数量、裁决、开始时间和结束时间，是唯一权威来源。
- `useAuditList`：最近成功列表、加载、局部错误和请求控制器；请求期间保留旧列表。
- `useGlobalAuditChain`：全局链结果、请求完成时间、加载、错误和请求控制器。
- `useAuditDetail`：当前 `auditId` 的详情、加载、错误和请求控制器。
- `useAuditVerification`：当前 `auditId` 的校验结果、校验完成时间、加载、错误和请求控制器。
- `useAuditExport`：一次性导出状态和局部错误，不保存导出原始对象。
- 页面：仅组合组件，不保存接口状态。
- `sessionStore`：不增加任何审计字段。

### URL 与列表数据流

`auditQueryParams` 解析地址参数并规范化。非法页码、每页数量、裁决或时间值回退默认值；开始时间晚于结束时间时显示本地错误且不请求。时间输入按浏览器本地时间展示，地址和接口统一保存 ISO 8601 UTC 字符串。

筛选或每页数量变化时写入第一页；页码变化只更新页码。浏览器前进、后退直接触发地址解析和新请求。旧请求先取消，并用请求序号防止迟到响应覆盖最新结果。空页且 `total > 0` 时按推导总页数修正地址。

进入详情时，仅携带规范化后的有效列表参数。详情控制器只用 `auditId` 调用详情、校验和导出接口；返回按钮重新构造 `/audits?...`。其他页面直接进入详情时不强制添加查询参数。

### 详情展示与适配

详情共享单份 `AuditDetailResponse`，按指令理解、证据核对、决策依据、安全告警、复核、授权、执行、时间线、完整性和导出分段展示。

`auditMapper` 只做枚举中文映射、缺失值处理、风险项提取和关联轮次链接生成，不重算业务结论。证据区使用真实需求、召回、缺失、强制召回、质量与冲突数据；完整图谱只通过当前轮次链接进入证据页。关联轮次从详情和工作流事件中提取已存在的根、父、当前和子轮次，不补造关系。

原始载荷和哈希默认折叠。详情适配会检测敏感键并隐藏；任何令牌值都不渲染、不复制、不写入日志。

### 校验、全局链与导出

详情进入后单条校验一次，支持手动重新校验，不轮询。切换 `auditId` 或卸载时同时取消旧详情和旧校验请求。校验失败只影响校验面板，不清空详情。

全局链失败不阻断列表。接口没有数量字段，因此只显示通过/异常、局部错误和本次页面校验完成时间。

导出仅由用户点击触发。响应先经 `auditSanitizer` 创建递归脱敏副本，再生成 JSON Blob；文件名使用清理后的 `auditId` 和 UTC 时间。原始对象与脱敏对象均不写入控制台或错误详情。

### 组件边界

列表页由页头、筛选条、链摘要、表格和分页组成。表格只展示真实列表字段：时间、指令摘要、动作、目标、风险、最终裁决、执行状态、轮次与详情链接；契约未提供的输入方式、授权和逐条完整性不显示虚假列。

详情页由页头以及指令、证据、决策、安全告警、复核、授权、执行、关系、时间线、校验和导出分区组成。组件只接收展示数据和回调，不调用 API。

### 异常与边界处理

- 列表首次失败展示整区错误；已有数据刷新失败时保留数据并展示局部错误。
- 无记录和筛选无结果使用不同空状态。
- 无效 `auditId` 停留当前地址；详情错误、校验错误和导出错误相互独立。
- 未知枚举显示安全的原始字符串或“未知状态”，不导致渲染失败。
- 长文本截断并可按需展开；原始 JSON 默认折叠。
- API 开发日志维持现有 URL 日志，但导出载荷和敏感字段永不记录。

### 测试与验证

单元测试覆盖查询参数解析和规范化、页码修正、时间校验、枚举映射、详情映射、未知枚举、关联轮次、敏感字段递归删除、导出文件名及校验状态。

完成后运行全部前端测试、类型检查和构建。真实接口验证覆盖默认列表、分页、每页数量、三种裁决、时间范围、无结果、前进后退、详情各分区、父子关系、单条校验、导出脱敏、无效编号、刷新恢复以及桌面和小屏布局。无法安全构造的完整性失败场景如实记录。

## 风险与待确认项

- 列表契约缺少部分期望列，按“只展示真实字段”原则省略，不追加后端请求或前端推断。
- 全局链契约缺少校验记录数和异常数，只显示后端实际结论。
- 工作流事件载荷结构允许扩展，展示层采用安全摘要和折叠原始载荷，不依赖未冻结的内部键。
