# 五维裁决评分机制实验说明

> 本文只描述当前工作区后端实际运行的五维评分实现，用于设计和复算实验。
> 事实基线日期：2026-08-13。代码继续变化时，应重新核对本文引用的函数。

## 1. 实验对象与边界

当前正式五维评分由 `DecisionService` 实现，入口为：

- `backend/app/services/decision/engine.py::DecisionService.assess_intents`
- `backend/app/services/decision/engine.py::DecisionService.decide`
- 配置加载位置：`backend/app/core/pipeline.py::CommandPipeline.__init__`
- 配置文件：`config/decision_policy.yaml`

五个维度在代码中的内部键名为：

| 实验名称 | 代码键 | 当前语义 | 数值方向 |
| --- | --- | --- | --- |
| C_sem | `Csem` | 语义清晰度 | 越大越好 |
| C_cov | `Ccov` | 强制证据覆盖度 | 越大越好 |
| C_trust | `Ctrust` | 已校验证据可信度 | 越大越好 |
| C_jb | `Cjb` | 越狱抑制度/安全度 | 越大越安全 |
| C_nec | `Cnec` | 场景必要性 | 越大表示越有真实安全必要性 |

五维软评分不是最终裁决的全部。生产主链同时存在：

1. 五维软评分及其 `score_decision`；
2. 独立的 EAS 证据对齐路由；
3. SafetyGate 硬安全门；
4. 运行能力、语义状态和多意图执行协议等后续约束。

实验必须分别记录 `safety_score`、`score_decision` 和 `final_decision`，不能用
`final_decision` 反推五维评分公式是否正确。

## 2. 当前生产计算链

```text
原始文本
  -> SemanticFrame / SemanticIntent
  -> EvidenceDemand
  -> 检索、强制召回和 IntentEvidenceResolution
  -> EvidenceQualityService（状态刷新、物理冲突、EAS）
  -> AdvancedValidationService（security_signals、物理冲突、jailbreak_risk）
  -> SafetyGateService
  -> DecisionService.assess_intents
       -> 每个正式子意图构造 scoped_frame
       -> DecisionService.decide 计算五维和子意图裁决
  -> 最保守的多子意图聚合
  -> 后续运行能力、语义状态、Token 和执行约束
```

正式评分是逐子意图进行的。`assess_intents` 对每个具有正式
`IntentEvidenceResolution` 的 `SemanticIntent` 单独评分：

- `scoped_frame.intents` 只包含当前子意图；
- `semantic_confidence` 和 `ambiguity_score` 取当前子意图自己的值；
- 强制证据类型、已验证类型和证据节点集合按 occurrence 隔离；
- SafetyGate 中的 occurrence 规则按当前子意图切片；
- 全局安全校验结果（包括 `jailbreak_risk`）由所有子意图共享。

occurrence 的唯一键是：

```text
(clause_index, intent_id)
```

## 3. C_sem：语义清晰度

### 3.1 公式

代码表达式：

```python
Csem = clamp(
    semantic_confidence
    * (1 - semantic_ambiguity_beta * ambiguity_score)
)
```

当前配置：

```text
semantic_ambiguity_beta = 1.0
```

`clamp(x) = max(0, min(1, x))`。

### 3.2 当前实际输入

`semantic_confidence` 来自语义包装层
`SemanticOrchestratorService._confidence`：

1. 找到当前 intent 对应的召回 target；
2. 取该 target 各个 channel 中非空 `score`；
3. 对这些 channel score 做算术平均；
4. 裁剪到 `[0,1]` 并保留 6 位小数；
5. 如果 target 或有效 score 不存在，confidence 使用 `0.5`。

当前正式语义包装层对生成的每个 resolved intent 返回：

```python
(round(confidence, 6), 0.0)
```

因此，当前能够进入正式逐意图评分的 resolved intent 通常满足：

```text
ambiguity_score = 0
C_sem = semantic_confidence
```

公式中的 ambiguity 惩罚仍然保留，但当前正式语义来源不会为 resolved intent
生成非零 `ambiguity_score`。

### 3.3 多意图语义聚合

顶层 `SemanticFrame` 使用：

```text
frame.semantic_confidence = min(各 intent.semantic_confidence)
frame.ambiguity_score     = max(各 intent.ambiguity_score)
```

但是正式主链不会直接用顶层最小值给所有子意图评分；
`assess_intents` 会恢复每个子意图自己的 confidence 后逐项评分。

### 3.4 实验变量

建议记录：

- 原始文本；
- intent_id、clause_index；
- 每个召回 channel 的 score；
- `intent.semantic_confidence`；
- `intent.ambiguity_score`；
- `Csem.value`、`Csem.actual_weight`、`Csem.contribution`。

如果要测量同义表达的语义评分稳定性，应保持车辆状态和证据完全相同，只改变文本。

## 4. C_cov：强制证据覆盖度

### 4.1 公式

对每个子意图：

```text
R = 该 occurrence 的去重 required_types

Covered = {
  evidence_type |
  节点属于该 occurrence 的 required_node_ids，且
  quality_label ∈ {VALID, SUSPICIOUS}
}

C_cov = |Covered| / |R|，当 |R| > 0
C_cov = 不适用（None），当 |R| = 0
```

因此分母是当前子意图 `EvidenceDemand` 经 resolution 后的强制证据类型数，
不是检索 Top-K 数、全部证据节点数或全部候选类型数。

### 4.2 不同状态是否计入覆盖

| quality_label | 是否进入 C_cov 分子 |
| --- | --- |
| `VALID` | 是 |
| `SUSPICIOUS` | 是 |
| `STALE` | 否 |
| `TAMPERED` | 否 |
| `MISSING` | 否 |

`SUSPICIOUS` 仍算“有覆盖”，其负面影响主要进入 C_trust、冲突规则和最终裁决。

强制召回本身不会自动增加覆盖。只有召回后的最终节点状态为 `VALID` 或
`SUSPICIOUS` 才进入分子；补召后仍为 `MISSING`、`STALE` 或 `TAMPERED` 不计入。

### 4.3 与缺失证据的关系

缺失一个强制类型会同时产生至少两类作用：

1. C_cov 的分子减少；
2. `MANDATORY_EVIDENCE_AVAILABLE` SafetyGate 规则可直接 BLOCK。

因此缺失证据实验中，低 C_cov 是软评分现象，而最终 BLOCK 往往是硬门现象。

### 4.4 多意图

每个 occurrence 使用自己的 `required_types_by_occurrence` 和
`required_node_ids_by_occurrence`，不会把另一子意图的同类型证据直接计入当前分母或
分子。整轮顶层展示的评分取最低数值子意图，完整结果应读取
`intent_safety_assessments`。

## 5. C_trust：已校验证据可信度

### 5.1 证据选择

`validated_types` 来源于该 occurrence 的全部 evidence binding：只要 binding
具有 `node_id`，其 evidence type 就进入 validated type 集合。这里既可能包含强制
证据，也可能包含已绑定的可选证据。

对每个去重后的 evidence type，代码在该 occurrence 的 `resolved_node_ids` 中选择一个
规范节点：

1. 时间戳较新的优先；
2. 时间戳相同时，`node_id` 较大的优先。

`MISSING` 和 `TAMPERED` 节点不会在选择阶段被静默丢弃。

### 5.2 公式

状态到可信度的固定映射为：

| 状态 | Q(status) |
| --- | ---: |
| `VALID` | 1.0 |
| `SUSPICIOUS` | 0.5 |
| `STALE` | 0.3 |
| `TAMPERED` | 0.0 |
| `MISSING` | 0.0 |

若选出的规范节点为 `E_validated`：

```text
C_trust = mean(Q(node.quality_label) for node in E_validated)
```

这是不加权算术平均。当前公式没有按证据类型重要性、来源、语义相似度、时效数值、
因果权重或 mandatory/optional 身份再次加权。

如果没有任何可选择的 validated evidence：

```text
C_trust = None
applicable = false
```

### 5.3 状态如何形成

`EvidenceQualityService._refresh_node` 在评分前刷新状态：

- 无时间戳 -> `MISSING`；
- 值为空或原状态为 MISSING -> `MISSING`；
- 值不满足证据值契约 -> 清空值并变为 `MISSING`；
- 完整性哈希不匹配 -> `TAMPERED`；
- 超过有效期或原状态为 STALE -> `STALE`；
- 物理证据冲突可把相关 `VALID` 节点改为 `SUSPICIOUS`。

虽然节点有连续的 `freshness`、`consistency`、`availability` 字段，C_trust 本身只读取
离散 `quality_label` 对应的 Q 值。连续 freshness 主要进入独立 EAS 指标。

### 5.4 实验变量

`DecisionScoreFactors.validated_trust_values` 已保存每个入选节点的：

- evidence_type；
- selected_node_id；
- selected_status；
- trust_value；
- selection_source。

实验复算 C_trust 时应优先使用这份 trace，而不是对全部检索节点求平均。

## 6. C_jb：越狱抑制度

### 6.1 方向与公式

底层 `jailbreak_risk` 越大表示越危险；C_jb 做了明确反向转换：

```text
C_jb = clamp(1 - jailbreak_risk)
```

因此：

- C_jb = 1：没有检测到越狱/冲突风险；
- C_jb = 0：风险为 1，越狱抑制度最低；
- C_jb 越大越安全，方向与五维总评分一致。

### 6.2 jailbreak_risk 计算

`AdvancedValidationService` 将以下项目转换为 conflict：

1. `SemanticFrame.security_signals` 中的每个安全信号；
2. 由原始文本进一步命中的安全绕过、直接接口调用或控制报文规则；
3. `EvidenceQualityService` 产生的物理证据冲突。

设：

```text
n     = conflict_count
s_max = max_severity，范围 0..3
λ     = conflict_decay_lambda，当前为 0.5
```

则：

```text
risk_base = 1 - exp(-λn)

severity_component = 0                              , n = 0
severity_component = 0.5 + 0.5 * s_max / 3          , n > 0

jailbreak_risk = clamp(max(risk_base, severity_component))
C_jb           = 1 - jailbreak_risk
```

每个 `security_signal` 至少生成一个 severity=3 的 conflict。因此只要该信号进入校验，
`severity_component=1`、`jailbreak_risk=1`、`C_jb=0`。

### 6.3 证据参与边界

当前 validator 在入口明确丢弃传入的 `evidence` 列表；它不会直接读取
`AUTHORIZATION_STATE` 或 `SYSTEM_MODE` 来计算 risk。

证据可以通过 `physical_conflicts` 间接影响 C_jb，但动态召回的授权状态、系统模式
本身目前不是 risk 公式的数值输入。这一点在声明一致性或安全上下文实验中必须单独
记录，避免把“已召回证据”误认为“已用于 C_jb”。

### 6.4 跨子意图作用

validation 在整轮级别只计算一次，并把同一个 `jailbreak_risk` 传给每个子意图。
所以一个子句产生的全局安全信号会让本轮所有已评分 occurrence 得到相同 C_jb。

## 7. C_nec：场景必要性

### 7.1 适用范围

当前只有配置中明确列出的安全关键意图适用：

| intent_id | intent_cap |
| --- | ---: |
| `BRAKE` | 1.0 |
| `DECELERATE` | 0.8 |

普通车门、车窗、空调、座椅和灯光控制不适用：

```text
C_nec.value = None
C_nec.applicable = false
C_nec.actual_weight = 0
```

它们不会因为“不紧急”得到 0 分扣分，而是触发现有权重重归一化。

### 7.2 公式

代码按 evidence type 选择时间戳最新的节点，然后计算：

```text
emergency_score = 1.0，若满足以下任一条件：
  - SERVICE_BRAKE_STATE.emergency_braking_detected 为真
  - SURROUNDING_OBJECT_STATE.collision_state 属于
    {COLLISION, IMMINENT, DETECTED, TRUE} 或可解释为真
否则 emergency_score = 0
```

对 BRAKE/DECELERATE：

```text
safety_evidence_score = max(
  0.9，若 front_obstacle_distance <= 5.0 m，
  0.9，若 brake_state 属于 {REQUIRED, EMERGENCY, ACTIVE}，
  0.0
)

safety_critical_score = intent_cap * safety_evidence_score

C_nec = clamp(max(emergency_score, safety_critical_score))
```

由此可得常见值：

- BRAKE，无必要性证据：0；
- BRAKE，有障碍或制动必要性证据：0.9；
- DECELERATE，有障碍或制动必要性证据：0.8 × 0.9 = 0.72；
- BRAKE/DECELERATE，有真实紧急或碰撞证据：1.0。

文本中的“紧急”等措辞不直接增加 C_nec；必须由证据字段支持。

### 7.3 实验注意点

`_necessity_score` 接收整轮 reasoning evidence，并按 evidence type 取最新节点；
适用性按当前 scoped intent 判断。多意图实验中应同时检查是否有其他子意图带入同类型
场景证据。

## 8. 权重、适用性与总分

### 8.1 配置权重

当前配置权重为：

| 维度 | configured_weight |
| --- | ---: |
| C_sem | 0.210 |
| C_cov | 0.255 |
| C_trust | 0.255 |
| C_jb | 0.255 |
| C_nec | 0.025 |
| 合计 | 1.000 |

初始化时会强制检查：

- 权重之和必须为 1；
- C_nec 不得大于 0.025；
- C_nec 不得大于 C_jb 的十分之一。

### 8.2 不适用维度的重归一化

设适用维度集合为 `A`，配置权重为 `w_i`：

```text
active_total = Σ(i∈A) w_i
actual_weight_i = w_i / active_total，若 i∈A
actual_weight_i = 0                  ，若 i∉A

safety_score = clamp(Σ actual_weight_i × C_i)
```

当前代码将最终 score 保留 4 位小数；各 factor 的 value、actual_weight 和
contribution 保留 6 位小数。由于总分使用舍入前的 contribution 累加，直接相加展示的
6 位 contribution 可能出现极小尾差。

普通非 C_nec 意图若其他四维均适用，实际权重为：

```text
C_sem   = 0.210 / 0.975 = 0.215384615...
C_cov   = 0.255 / 0.975 = 0.261538462...
C_trust = 0.255 / 0.975 = 0.261538462...
C_jb    = 0.255 / 0.975 = 0.261538462...
C_nec   = 0
```

实验复算必须使用 `actual_weight`，不能始终用 configured weight。

## 9. score_decision 的真实规则

正常情况下：

```text
PASS   : score >= 0.75
REVIEW : 0.50 <= score < 0.75
BLOCK  : score < 0.50
```

但 `score_decision` 还有两个重要前置分支：

1. 若语义不完整，则固定为 REVIEW；
2. 若存在 validation conflict，或当前 occurrence evidence 中存在
   `SUSPICIOUS` 节点，则禁止直接 PASS：
   - score >= 0.50 -> REVIEW；
   - score < 0.50 -> BLOCK。

因此“总分高于 0.75”不是 `score_decision=PASS` 的充分条件。

## 10. EAS 与 SafetyGate：不要当作第六、第七维

### 10.1 EAS 证据对齐路由

EvidenceQualityService 还计算独立的 EAS：

```text
EAS = w_ecr*ECR + w_ecs*ECS + w_ef*EF + w_sas*SAS
```

其中：

- ECR：证据覆盖；
- ECS：证据一致性；
- EF：证据 freshness 平均值；
- SAS：语义相似度平均值。

EAS 使用 default/high_speed/complex_road 配置档，并将有效项权重重归一化。路由为：

```text
EVIDENCE_PASS   : EAS >= 0.85
EVIDENCE_REVIEW : 0.60 <= EAS < 0.85
EVIDENCE_BLOCK  : EAS < 0.60
```

没有强制证据需求时，EAS 数值仍可用于审计，但路由固定为 `EVIDENCE_PASS`。

EAS 与 C_cov 有部分输入重叠，但它不是五维总分中的额外权重项，而是在后续 merge 中
独立约束 `final_decision`。

### 10.2 SafetyGate

SafetyGate 可因以下类型直接 BLOCK：

- 强制证据缺失、篡改、过期或平均可信度不足；
- severity=3 的越狱冲突；
- 行驶中开门等车辆硬规则；
- 真实道路安全绕过、未授权接口或控制帧；
- 非驾驶员驾驶控制、障碍物条件等规则。

合并优先级的核心行为是：

```text
SafetyGate BLOCK -> final_decision 必为 BLOCK
否则 EVIDENCE_BLOCK -> BLOCK
否则 EVIDENCE_REVIEW -> REVIEW（除非 score 已 BLOCK）
否则 final_decision 继承 score_decision 或其他约束
```

硬门命中时五维仍会计算，但 `score_evaluation_mode` 为
`diagnostic_after_gate`，该分数只能用于诊断，不能抵消硬门。

## 11. 多意图聚合

每个子意图先独立得到：

- 五维 factor；
- safety_score；
- score_decision；
- occurrence SafetyGate；
- final_safety_decision。

整轮聚合规则为：

1. `aggregate_safety_decision` 取最严重子意图，顺序为
   `BLOCK > REVIEW > PASS`；
2. 顶层 `score_decision` 取最严重的子意图 score decision；
3. 顶层 `safety_score` 和 `score_factors` 取数值最低的子意图；
4. 多意图即使所有安全结果为 PASS，当前执行协议也会把整轮 final decision 降为 REVIEW；
5. 顶层 SemanticFrame 为 REVIEW 时，整轮 final decision 至少为 REVIEW；
6. 全局 validation risk 会作用于所有子意图。

“最严重裁决子意图”和“最低数值子意图”理论上可能不是同一个。因此多意图实验必须读取
完整 `intent_safety_assessments`，不能只分析顶层 factors。

## 12. 未评分与 REVIEW 安全诊断

普通 REVIEW、NO_MATCH、无 resolved formal intent 的输入会在评分前终止：

```text
five_factors = {}
intent_safety_assessments = []
score_decision = REVIEW
final_decision = REVIEW
```

当前唯一允许 REVIEW 继续安全链的条件为：

```text
semantic_status == REVIEW
且至少存在一个 runtime_identity == FORMAL 的 resolved intent
且 security_signals 非空
```

该路径会为 resolved formal intent 执行真实证据、validation、C_jb、SafetyGate 和五维
诊断，但顶层 REVIEW 仍不会获得执行授权。

未进入五维评分的记录中可能仍保留历史兼容 `safety_score=1.0`。实验判定“是否评分”时
必须以 `five_factors` 或 `intent_safety_assessments` 是否为空为准，不能只看
`safety_score`。

### 14.2 隔离实验变量

建议把实验分成五组单因素控制：

| 目标维度 | 保持不变 | 主要操纵变量 |
| --- | --- | --- |

| C_trust | 文本、覆盖类型 | VALID/SUSPICIOUS/STALE/TAMPERED/MISSING |
| C_jb | 车控意图和车辆状态 | security signal、冲突数、最高 severity |
| C_nec | BRAKE/DECELERATE 文本 | 碰撞、障碍距离、制动状态证据 |

每个 case 建议新建独立 `CommandPipeline` 和独立审计数据库，避免历史 evidence、memory
或工作流状态相互污染。虽然 causal confidence 当前不进入五维总分，隔离仍能保证完整
管线结果可复现。

### 14.3 时间控制

证据状态和 freshness 依赖决策参考时间。过期实验应使用可信 evidence override 的
`age_seconds`/有效期字段构造，不要依赖真实 `sleep`，否则重复实验可能出现时间漂移。

### 14.4 每个 case 的复算检查

```text
1. 确认是否真实进入五维：five_factors 非空
2. 确认 occurrence 和 required_types
3. 根据节点最终 quality_label 复算 C_cov
4. 根据 validated_trust_values 复算 C_trust
5. 根据 conflict_count/max_severity 复算 jailbreak_risk 与 C_jb
6. 根据证据字段复算 C_nec，并核对 applicable
7. 根据 applicable 集合重归一化权重
8. 求和并按 4 位小数核对 safety_score
9. 根据冲突分支和阈值核对 score_decision
10. 最后单独核对 EAS、SafetyGate 和 final_decision
```

## 15. 当前实现中影响实验解释的事实

以下不是修改建议，而是解释实验结果时必须纳入的当前事实：

1. 当前正式 resolved intent 的 ambiguity_score 为 0，所以 C_sem 实际等于 confidence。
2. C_cov 把 SUSPICIOUS 计为已覆盖，但 C_trust 对它只计 0.5。
3. C_trust 是所有已绑定规范类型的等权平均，可选证据也可能参与。
4. freshness 连续值不直接进入 C_trust，但会进入独立 EAS。
5. 任意 security_signal 会产生 severity=3 conflict，从而使 C_jb 直接变为 0。
6. AUTHORIZATION_STATE 和 SYSTEM_MODE 的召回不代表它们参与了 C_jb 风险公式。
7. C_nec 只对 BRAKE/DECELERATE 适用；普通控制通过权重重归一化排除该维度。
8. 全局 jailbreak risk 会重复应用到每个子意图。
9. SafetyGate BLOCK 无法被高五维分抵消。
10. EAS 与 C_cov/C_trust 有输入关联，但作为独立裁决路由再次影响 final decision。
11. 多意图顶层 score 取最低分 occurrence，而最终标签取最严重 occurrence。
12. `five_factors={}` 才表示未评分；兼容 safety_score 数字本身不能证明评分已执行。

## 16. 合理性与准确性实验建议

### 16.1 先验证实现可复算性

第一层实验不评价算法优劣，只确认实际输出与代码公式一致。对每个 occurrence 计算：

```text
factor_error_i = |代码输出的 C_i - 实验脚本复算的 C_i|
weight_error   = |Σ applicable actual_weight - 1|
score_error    = |代码 safety_score - 实验脚本复算 score|
```

建议接受误差按代码舍入精度设置：factor 使用 6 位小数，总分使用 4 位小数。

### 16.2 单调性实验

在其他输入固定时，检查当前机制是否满足预期方向：

| 操纵 | 代码机制预期 |
| --- | --- |
| semantic confidence 降低 | C_sem 与总分不升高 |
| 缺失更多 mandatory types | C_cov 与总分不升高 |
| VALID 改为 SUSPICIOUS/STALE/TAMPERED | C_trust 与总分不升高 |
| conflict 数或最高 severity 增加 | jailbreak_risk 不降低，C_jb 不升高 |
| BRAKE 的真实必要性证据增强 | C_nec 不降低 |

这里要同时检查离散跳变。例如一个 security signal 会直接产生 severity=3，导致
C_jb 从 1 跳到 0，而不是连续下降。

### 16.3 标签准确性实验

若数据集有人工标注的 PASS/REVIEW/BLOCK，可分别评估：

1. `score_decision` 对标签的混淆矩阵、Macro-F1、各类召回率；
2. `final_decision` 对标签的同一组指标；
3. SafetyGate 命中样本的 BLOCK 召回率和误阻断率；
4. 有/无 validation conflict 两个子集的指标；
5. 单意图与多意图两个子集的指标；
6. 每种 canonical intent 的分组指标。

`score_decision` 衡量五维软评分及其冲突分支，`final_decision` 衡量完整安全链；两者必须
分开报告，否则无法定位误差来自五维、EAS 还是硬门。

### 16.4 连续分数评估

当前 `safety_score` 是加权安全指标，不是经过概率校准的“安全概率”。因此：

- 可以评估安全/危险样本的分数分布、排序 AUC、阈值敏感性；
- 可以比较类内方差、类间距离和不同 intent 的分布漂移；
- 不应未经额外校准就把 0.80 解释为“80% 安全概率”；
- Brier Score、ECE 等概率校准指标只有在先定义概率语义后才有解释力。

### 16.5 消融分析

无需改生产代码，可以基于已记录的 factor value 和 applicability 离线复算：

```text
完整五维分数
去掉某一维后按现有规则重归一化的分数
单独使用某一维的排序结果
```

比较消融前后的 Macro-F1、危险样本召回率和误阻断率，可量化每个维度的实际贡献。
离线消融结果不能替代生产主链结果，应在实验表中明确标记为 `offline_recomputed`。

### 16.6 推荐最小数据表

每行对应一个 occurrence，至少保存：

```text
case_id
raw_text
clause_index
intent_id
semantic_status
semantic_confidence
ambiguity_score
required_types
resolved evidence type/status/node_id
conflict_count
max_severity
jailbreak_risk
Csem/Ccov/Ctrust/Cjb/Cnec 的 value/applicable/actual_weight/contribution
safety_score
score_decision
EAS 与 evidence_alignment_route
SafetyGate hit_rules
final_safety_decision
顶层 final_decision
人工标签
```

多意图轮次还应保留 `turn_id`，用于把 occurrence 行重新聚合到整轮。
