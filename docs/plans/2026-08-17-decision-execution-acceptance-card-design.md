# 裁决页常驻执行验收卡设计

## 背景与目标

当前裁决页只突出最终裁决，执行授权与拒绝原因分散在确认弹窗和页面底部；HTTP 409 等真实执行拒绝未被稳定展示，导致令牌重复使用与签发后状态变化无法从前端清晰验收。

目标是在“具体原因”之后增加一个常驻、面向人的执行验收卡。它展示真实后端执行结果，不展示原始 token，不修改安全裁决、评分、token 签发或执行语义。

## 现状与约束

- `POST /api/turns/{turn_id}/execute` 可能返回正常 `ExecuteResult`，也可能以 409 返回授权冲突原因。
- token 只保存在 React 内存，不可写入 Web Storage。
- 验收模式必须适用于任何指令；未签发授权时必须明确说明不可执行。
- 裁决顶部大字已经表示最终结果，因此不保留重复的“最终裁决”字段。

## 方案对比

### 方案一：裁决页常驻验收卡（采用）

- 优点：所有指令都有一致入口，测试状态和真实结果集中可见，最适合演示。
- 缺点：裁决页增加一个固定区域。

### 方案二：仅 PASS 后显示

- 优点：页面更紧凑。
- 缺点：失败/复核时用户不知道为何无法测试，不满足验收可解释性。

### 方案三：独立验收页面

- 优点：功能隔离。
- 缺点：增加路径，不利于在裁决上下文中解释执行结果。

## 详细设计

### 页面结构

1. 删除裁决结果内的“裁决来源”“合并原因”“最终裁决”字段。
2. 在“具体原因”之后固定显示“执行验收”卡。
3. 卡片左侧为模式选择：正常执行、重复使用同一授权、签发后改变状态。
4. 卡片中部显示当前执行状态；右侧只显示最近一次真实后端执行结果。
5. 删除现有页面底部执行说明与结果堆叠；token 不展示。

### 状态机

- 无当前轮次 / 不可执行裁决：显示“未签发授权，无法执行所选验收模式”。
- PASS 且确认弹窗未确认：显示“等待确认执行”。
- 确认后：保存 token 于内存并显示“授权已签发”。
- 正常执行：一次真实执行请求。
- 重复使用：先执行一次，再用同一内存 token 发起第二次真实请求。
- 状态变化：签发后提示去模拟器修改状态；返回后以原 token 发起真实执行。
- 任何 HTTP 409：从 API 错误详情提取后端原因，作为“已拒绝”展示。

### 数据与安全边界

- 后端仍是所有安全决定和执行结果的唯一来源。
- 前端不制造 token、不在 local/session storage 保存 token、不把 token 放入 DOM。
- 对非 PASS 或无 token 情况，前端不发执行请求。

### 验收标准

- 普通拒绝指令显示不可执行原因。
- token_reuse：首次执行成功后，第二次显示后端真实拒绝原因（已消费或已过期）。
- state_changed_before_execution：修改安全状态后显示“签发后安全相关车辆状态发生变化”。
- 任意 409 不再表现为“点击没有反应”。
- 页面不再显示裁决来源、合并原因、重复最终裁决或散落执行说明。
