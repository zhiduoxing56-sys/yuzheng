# 前端真实入口 23 场景验收设计

## 背景与目标

此前 23 场景仅通过后端 scenario runner 验收，不能证明用户在前端文本入口、确认与执行流程中得到相同结果。目标是从 `http://127.0.0.1:5173` 的用户入口重新验收全部正式场景，找出所有与正式契约不一致的问题。

## 现状与约束

- 不以 `/api/scenarios/{id}/run` 的结果作为前端验收结论。
- 每条先经前端加载场景状态，再经页面文本入口提交正式 `input_text`。
- 记录页面展示与实际 HTTP payload/response，特别是身份、区域、session、确认和 token。
- token 重用与签发后状态变化必须完成确认与执行时序。
- 本阶段先审计，不通过降低契约或修改代码掩盖问题。

## 方案对比

### 方案一：真实前端入口验收（采用）

通过浏览器页面操作并捕获其 API 请求/响应，验证用户实际看见的裁决和交互。

### 方案二：复放前端 HTTP 请求

可验证接口但不能验证页面展示和交互，因此不作为验收依据。

### 方案三：后端 scenario runner

仅验证后端状态注入路径，已证实不能代表前端用户路径。

## 详细设计

每条场景按以下数据流记录：

```text
场景状态 → 前端文本输入 → 前端提交 payload → API response
→ 页面展示 → interaction/token → execute → 最终状态
```

输出字段包括输入、状态、提交身份字段、intent、slots、runtime identity、安全门、证据对齐、裁决、原因、token、执行与最终车况。每项与正式契约对照，问题归类为前端状态/身份传递、前端展示/交互、API/语义、安全门/证据或 token/execution。

## 已确认风险

自由文本 `立即制动` 已复现为 `EMERGENCY_BRAKE` 却命中 `NON_DRIVER_DRIVING_CONTROL_PROHIBITED`。scenario runner 会注入可信 `subject_role=driver`，前端文本链路没有等价身份上下文；必须以真实入口结果为准。

## 本地验收时序演示

裁决页的既有确认执行区域将增加仅在正式 token 验收场景出现的“授权生命周期演示”卡片，视觉复用现有裁决卡片、蓝色按钮和中文字体，不展示、复制或记录原始 token。

- `token_reuse`：首次执行后，可触发一次受控的“再次执行同一授权”，页面展示已消费/拒绝状态。
- `state_changed_before_execution`：签发后可暂停执行，用户回模拟器更改状态，再按原授权执行，页面展示重新核验结果。
- 普通用户路径仍保留原有“确认即执行”行为；演示操作只以当前轮次和内部交互标识调用现有执行接口，不修改 token、安全门或执行算法。

## 测试策略

先建立 23 条完整问题矩阵；随后仅修复已由真实链路证实的生产断链，并重新进行前端全量回归。
