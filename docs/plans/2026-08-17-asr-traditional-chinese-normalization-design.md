# ASR 繁体中文归一设计说明

## 背景与目标

本地 Whisper 中文转写可能产出繁体字。当前语义规范化只处理 Unicode 兼容形式、空白及大小写，繁体文本直接进入冻结语义编排器，可能因字形不匹配产生不必要的 `REVIEW`。

目标是在不丢失原始 ASR 证据的前提下，将繁体中文自动转换为简体中文后参与语义识别与后续裁决；字形差异本身不应阻断自动执行。

## 现状与约束

- `TranscriptionResult.text` / `transcribed_text` 是 ASR 原始转写及审计输入，两个字段必须一致。
- 音频流水线将 `transcription.transcribed_text` 传给 `process_text()`；`SemanticFrame.normalized_text` 由语义服务生成。
- 语义、检索与 review 都依赖进入 `process_text()` 的文本或其语义帧。
- 转换不能覆盖原始 ASR 转写，必须保留审计可追溯性。
- 转换服务不可用或结果异常时必须 fail-closed：进入 `REVIEW`，不得以未经规范化的繁体文本自动执行。

## 方案对比

### 方案一：覆盖 ASR 转写为简体

- 优点：改动范围小。
- 缺点：丢失 ASR 原始证据，审计与问题定位不可追溯。

### 方案二：仅在 review 页面转换

- 优点：不改变后端语义链路。
- 缺点：不能消除繁体字引发的 `REVIEW`，不满足自动执行目标。

### 方案三：保留原文，增加语义归一文本（推荐）

- 优点：原始 ASR 文本完整留存，解析/检索统一使用简体文本；边界和审计清晰。
- 缺点：需要新增可测试的转换适配层及转换异常处理。

## 推荐方案

在 ASR 成功后、调用 `process_text()` 前生成简体中文的语义输入。`TranscriptionResult` 继续保存原始繁体转写；语义帧中的 `raw_text` 和 `normalized_text` 均基于归一后的输入，使后续路由、语义识别、检索、review 候选和裁决使用同一文本。

## 详细设计

### 架构与数据流

`音频 → ASR 原始转写 → 简繁归一 → process_text / 语义解析 / 检索 / 裁决`。

原始 ASR 文本保存在 `AudioCommandResponse.asr_result`、工作流 ASR 事件和审计的转写结果中；归一文本通过语义帧与既有 `normalized_text` 对外呈现。归一后文本与原文不同的时候，在工作流事件中记录原文和归一文本及转换适配器，以便审核复现。

### 关键组件

- 新增纯函数/轻量服务，使用项目已安装、离线可用的 OpenCC 简繁转换能力，将 `t2s` 用于 ASR 输出。
- 只在音频 ASR 路径调用；文本 API 保持用户原始输入语义，避免意外改写明确输入。
- 转换输出为空、转换器加载失败或转换过程报错时，生成明确原因的终态 `REVIEW`，不进入语义与执行链。

### 异常与边界处理

- 简体输入经过转换后保持等价，可以照常自动执行。
- 标点、ASCII、数字和车控专名保持转换器默认行为，不另行猜测同音词或 ASR 错字。
- 简繁转换只解决字形差异，不降低现有 ASR 置信度、语音可信、权限和安全门控；这些门控仍可得到 `REVIEW` 或 `BLOCK`。

### 测试策略

- 单元测试：繁体车控指令转换为预期简体；纯简体输入保持不变。
- 流水线测试：模拟 ASR 返回繁体文本，验证传给 `process_text` 的文本为简体，而响应与审计 ASR 文本仍是原文。
- 异常测试：转换器故障时结果为 `REVIEW`，且没有授权令牌或执行请求。

## 风险与待确认项

- 若当前固定环境没有 OpenCC 依赖，需要以已安装的等价离线库实现，或经用户批准新增受控依赖；不调用在线转换服务。
- UI 若当前只显示 `asr_raw_text`，可沿用原样；归一结果已经通过既有 `normalized_text` 可见。
