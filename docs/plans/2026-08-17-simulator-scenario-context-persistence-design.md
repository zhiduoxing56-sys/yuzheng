# 模拟器场景上下文持久化设计说明

## 背景与目标

当前“载入场景”只在所有补充证据来源均为 `SIMULATION` 时才保存补充证据。双源车速冲突使用 `speed_a`、`speed_b`，载入后仅保留 `0 km/h / P` 的车辆镜像状态，后续指令看不到冲突证据并可能被放行。

目标是让用户选择的场景和上下文持续作为当前仿真事实：普通指令和无关执行动作不得清空它；用户主动切换场景或重置时清空全部旧上下文；用户手动修改某类状态时，以该修改替换同类场景事实。

## 现状与约束

- `SimulatorVehicleAdapter` 仅接受来源为 `SIMULATION` 的持久场景证据。
- `update_state` 与 `execute` 会清空所有场景证据。
- 车速冲突需要保留不同 `source` 才能被质量服务识别。
- CARLA 适配器的补充上下文仍仅允许 `SIMULATION`，其物理车速由 CARLA 自身拥有；本次不能放宽该边界。

## 方案对比

### 方案一：适配器持久化完整场景证据（推荐）

- 优点：场景事实与历史审计分离；支持多源同类证据；符合当前适配器职责。
- 缺点：需要为状态更新和执行动作增加按类型失效规则。

### 方案二：把场景证据写入全局证据仓库

- 优点：改动表面较小。
- 缺点：会与历史、过期和检索证据混合，不能可靠表达当前场景。

### 方案三：每个命令重新读取 YAML 场景

- 优点：不需保存上下文。
- 缺点：无法反映用户在面板中的后续状态调整。

## 推荐方案

采用方案一。模拟器适配器保存场景提供的全部证据，不再限制其来源命名。场景加载、切换和重置替换完整集合；手动状态更新只删除与更新字段对应的证据类型；执行车辆动作只删除与实际被改变字段对应的场景证据。

## 详细设计

### 数据流

1. 载入场景时，模拟器适配器保存完整 `evidence_overrides`，包括 `speed_a`、`speed_b`。
2. 每次处理指令时，管线从适配器读取该集合并随本轮快照注入。
3. 用户修改车辆状态时，适配器根据更新字段移除关联场景证据，例如 `vehicle_speed` 对应 `VEHICLE_SPEED`。
4. 执行物理命令后，根据命令实际写入的状态字段移除关联证据；无关证据保持不变。

### 边界处理

- 切换场景通过场景激活直接替换旧集合。
- 重置清空集合。
- 不支持的或无映射的状态字段不清除场景证据。
- CARLA 的补充上下文来源约束保持不变，避免把 CARLA 自有物理状态伪装成补充证据。

### 测试策略

- 载入双源车速冲突后，连续“打开车门”均不可 PASS。
- 普通执行动作后，未受该动作影响的场景证据仍存在。
- 手动修改车速后，旧双源车速证据被清除，当前快照成为唯一车速事实。
- 切换场景和重置后，旧场景证据均被清除。
