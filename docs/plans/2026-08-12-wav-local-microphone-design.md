# WAV 上传与本机麦克风输入设计说明

## 背景与目标

新版裁决页目前仅文本提交真正接入后端。目标是在不引入浏览器录音编码的前提下，恢复两条已有能力：其他笔记本可上传 PCM WAV；本机部署时可由后端进程调用本机麦克风采集语音。

## 现状与约束

- 后端已有 `POST /api/command/audio` 和 `POST /api/command/microphone`。
- 音频解码器仅接受未压缩 PCM WAV，时长范围为 0.35～15 秒。
- 麦克风接口操作的是后端进程所在电脑的音频设备；当前项目在用户笔记本本机运行，因此满足需求。
- 不实现浏览器 `getUserMedia`，也不宣称支持 MP3、M4A、FLAC 或 OGG。

## 方案对比

### 方案一：复用后端音频与麦克风接口（采用）

- 优点：改动小；继续使用现有 ASR、语音可信与审计链路；符合本机部署条件。
- 缺点：若将来把后端部署到远程服务器，麦克风会变成服务器麦克风。

### 方案二：浏览器录音后上传

- 优点：远程部署时仍使用访问者的麦克风。
- 缺点：需要浏览器权限、录音编码和兼容性处理，本阶段不需要。

### 方案三：调用 Windows 录音机

- 优点：用户熟悉系统应用。
- 缺点：网页不能安全地自动读取系统录音机生成的文件，不适合作为闭环输入方式。

## 详细设计

### 数据流

- WAV：选择文件 → 校验扩展名与 20 MiB 上限 → 原始字节提交 `/api/command/audio` → 展示响应语义帧 → 更新 URL 的 `turn_id`。
- 本机语音：点击麦克风按钮 → 请求后端采集 4 秒 → 后端完成 WAV 编码和语音流水线 → 展示响应语义帧 → 更新 `turn_id`。

### 异常与边界处理

- 非 WAV、空文件和超限文件在前端阻止提交。
- 后端负责验证 WAV PCM 编码、实际音频时长、麦克风设备、ASR 和可信模型状态。
- 页面切换轮次或发起新请求时取消旧请求。
- 麦克风采集期间禁用重复操作，并明确显示“本机麦克风采集中”。

### 测试策略

- 回归文本提交。
- 验证 WAV 文件原样提交并更新语义帧、URL。
- 验证非 WAV 文件不会调用接口。
- 验证麦克风请求使用 4 秒、本机默认设备并更新语义帧、URL。

## 后续风险

若后端迁移到远程服务器，应停用后端麦克风入口并改用浏览器录音上传。
