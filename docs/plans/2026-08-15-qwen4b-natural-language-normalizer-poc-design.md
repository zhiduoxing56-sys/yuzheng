# 四十亿参数自然语言规范化器隔离概念验证

## 背景与目标

验证 `qwen3.5:4b` 是否能将完整原始自然语言切分为保持顺序的极短规范语义单元，而不生成完整语义帧、不执行路由或安全裁决。输出仅为 `{"u":[[类型,"标准句"]]}`，类型为车控、上下文、非车控或不确定。

## 约束

不修改正式生产链、ClauseResolver、Registry、EvidenceDemand、安全、授权、执行或前端；不下载模型。4B 直接读取原文，禁止先用 ClauseResolver。规范化阶段结束后卸载 4B，才对类型 0 标准句调用现有 `SemanticOrchestratorService.parse()`，确保离线串联且模型不并驻留。

## 方案对比

### 方案一：仅评估规范化

速度快，但无法验证标准句与现有 SemanticFrame 的兼容性。

### 方案二：规范化后逐条二次解析（采用）

保留模型职责边界，并直接暴露现有解析器无法消费的规范句；失败只报告，不添加规则。

## 详细设计

使用完整 JSON Schema 约束最小输出，设置 `think=false`、`temperature=0`、`num_ctx=2048`、`stream=true`、`keep_alive=-1`。测试集覆盖口语数值、区域、上下文、否定、混合/多意图、71/78 范围外车控。24 条金标原文各执行两次，共 48 次热启动；另执行三次预热和一次冷启动。

逐项记录原始输出、单元数量/顺序/类型、标准句、否定/区域/数值保留、JSON 与合约有效性、性能及安全关键错误。类型 0 的规范句去重后逐条送入未修改的正式语义解析器，记录 SemanticFrame 或失败。

## 判定

以用户给出的示例和类别要求为人工金标。标准句允许等价表述，但不得丢失原有动作、对象、区域、明确数值、否定、条件或限制，也不得虚构动作或系统状态。最终分别报告规范化性能、模型切分相对 ClauseResolver 的稳定性、二次解析兼容性和是否值得替换完整 4B 语义输出设计。
