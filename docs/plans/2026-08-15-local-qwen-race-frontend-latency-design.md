# 本机千问赛马测试与前端总耗时设计说明

## 背景与目标

仅对本机 Ollama 模型进行隔离赛马：正式基线为 `qwen2.5:3b-instruct-q4_0`，候选优先为 `qwen3.5:9b-q8_0`。复用正式请求路由的提示词、结构化输出合约和生成参数，使用人工确认的有序子句，避免 ClauseResolver 影响模型能力结论。不得修改正式前端、生产请求路由、模型配置或安全链。

新增指标 `frontend_end_to_end_ms`。它表示模拟前端客户端从开始构造并发起请求，到流式响应完整接收、内容拼接、JSON 解析和输出合约校验成功（或失败已被记录）为止的墙钟时间。

## 现状与约束

正式前端不直接调用 Ollama；本机模型调用位于 `RequestRoutingService`。因此真实 UI 到 API 的耗时会混入后端管线和页面渲染，不能作为本轮模型隔离赛马指标。基准客户端将模拟前端对模型接口的可见完整交互，并与 Ollama 返回的服务端时长分开记录。

## 方案对比

### 方案一：真实浏览器端到端

- 优点：最接近用户体验。
- 缺点：混入页面、API 和生产管线，不再是模型隔离测试。

### 方案二：隔离基准客户端端到端（采用）

- 优点：两个模型的请求构造、HTTP 流、收包、JSON 解析和合约校验完全一致；可与 Ollama 指标直接对照。
- 缺点：不包含真实 UI 渲染和正式 API 其他处理。

### 方案三：只记录 Ollama 服务端时长

- 优点：实现最简单。
- 缺点：遗漏网络/流式传输和客户端处理，不满足需求。

## 详细设计

临时基准脚本为每一次冷启动、预热和热启动调用记录：

- `frontend_end_to_end_ms`：客户端从请求开始到 JSON 解析与 Pydantic 合约校验结束；
- `first_token_latency_ms`：开始请求到首个内容分片；
- Ollama 原始指标：总时长、模型加载、提示词处理、输入词元、生成时长、输出词元和生成速度；
- 解析/合约状态与错误信息。

热启动汇总会单列 `frontend_end_to_end_ms` 的均值、中位数和 P95；冷启动单独报告，绝不混入热启动统计。最终模型资源对比表与逐条语义结果表均显示该字段。

## 异常与边界

请求失败、流中断、非法 JSON 或合约失败仍记录已经消耗的 `frontend_end_to_end_ms`，并标记失败原因；不得以重试替换原始失败样本。任何模型标签不存在、未完全 GPU 驻留或发生 CPU 卸载也只记录证据和结论，不调整正式配置。

## 测试策略

用正式提示词与输出合约对两模型运行同一人工分句样本集：先预热，再对每个样本至少三次热启动，并各记录一次冷启动。验证每行均同时包含客户端端到端指标、Ollama 指标与结构/语义/安全评分，最后生成 JSON 原始结果和 Markdown 报告。
