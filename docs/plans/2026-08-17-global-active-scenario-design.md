# 全局激活场景一致性设计说明

## 背景与目标

当前场景覆盖由车辆适配器保存。Simulator 与 CARLA 对“物理自有证据”的处理不同，导致切换页面或通过 CARLA 载入场景后，裁决链路可能没有使用用户刚设置的完整场景。

本设计将当前激活场景提升为 `CommandPipeline` 的全局唯一事实源。所有用户共享同一辆模拟车和同一激活场景；裁决页、CARLA 页、文本/语音 API 均读取同一份场景事实。

## 现状与约束

- 车辆物理状态由适配器提供，CARLA 可实时回读部分物理字段。
- 场景中的多源覆盖证据（例如 `speed_a`/`speed_b`）必须完整保留，不能被适配器过滤。
- 用户手动修改车辆事实时，该事实必须替换相同证据类型的场景覆盖。
- 普通指令、页面跳转和无关执行动作不得清空场景。
- 所有用户共享全局场景，任一用户切换场景即对所有用户生效。

## 方案对比

### 方案一：管线级全局激活场景（采用）

- 优点：适配器无关；全部入口共享；审计可证明裁决实际使用的场景；能防止同类问题在新适配器重现。
- 缺点：需要增加场景状态模型、同步与审计字段。

### 方案二：扩展各车辆适配器的场景证据

- 优点：改动较小。
- 缺点：业务事实分散，CARLA 与后续适配器仍可能产生不一致。

### 方案三：前端每次命令带入当前场景

- 优点：接口实现简单。
- 缺点：刷新、音频入口、直接 API、多用户会失去一致性，不能作为安全事实来源。

## 详细设计

### 全局场景状态

新增管线内部 `ActiveScenarioContext`：

- `scenario_id`、`name`、`version`、`activated_at`；
- 完整 `evidence_overrides`；
- 对应的场景物理状态基线；
- 当前仍有效的覆盖证据。

场景加载在同一命令锁内完成：重置车辆、应用场景物理状态、原子替换全局场景上下文。重置清空它；加载另一场景完整替换它。

### 裁决和状态变更

每次 `process_text()` 统一合并：当前物理快照 + 全局场景有效覆盖 + 本次可信临时覆盖。适配器不再是场景覆盖的来源。

用户通过状态面板修改字段时，管线根据字段到证据类型的映射，移除全局场景中同类型覆盖；例如修改 `vehicle_speed` 会移除全部 `VEHICLE_SPEED` 覆盖。普通车辆执行也仅让其实际改写字段对应的场景覆盖失效，无关覆盖不变。

审计与事件记录激活场景 ID、版本和证据摘要，确保每一轮可追溯其实际场景。

### CARLA 页面展示

CARLA 实时画面下方现有空白区域增加只读“当前激活场景”摘要：场景名称、ID、版本、激活时间、关键物理状态和覆盖证据数量/类型。页面重新进入时从后端读取该摘要；不得用默认草稿或页面本地状态覆盖它。

### API

新增只读端点返回全局激活场景摘要与有效覆盖；场景加载、状态更新和重置沿用既有端点，但响应后摘要版本发生相应变化。

### 测试策略

- Simulator 和 CARLA 均在载入双源车速冲突后，对连续开门命令保持非 PASS。
- 场景加载后的审计包含同一场景 ID/版本及冲突覆盖。
- 手动修改车速仅移除车速覆盖；无关上下文仍保留。
- 普通执行、裁决页面往返不会改变全局场景版本。
- 切换场景和重置按预期替换或清空全局场景。
- CARLA 页面在重新挂载时读取并展示后端摘要。
