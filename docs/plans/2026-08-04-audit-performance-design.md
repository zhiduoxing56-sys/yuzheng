# 后端审计性能专项修复设计

## 背景与目标

审计列表原先在数据库分页前解析全部完整审计，并对每条记录分别查询复核结果和执行状态；全局链校验则在每次请求中重新读取、反序列化和散列整条链。目标是在不改变冻结接口和业务结论的前提下，使常用列表低于 1 秒、缓存链校验低于 100 毫秒，并消除并发重复计算。

## 方案对比

1. 仅延长前端超时：不减少后端工作量，会继续堆积慢任务，不采用。
2. 在原始 JSON 上增加 SQL 分页：能减少列表载荷，但有效裁决、语义帧和执行状态仍需要额外解析或逐条查询，收益不稳定。
3. 独立紧凑摘要表 + 批量状态查询 + 增量链校验：保留原始载荷与冻结响应，查询次数固定，支持安全回填与回滚。采用此方案。

## 架构与数据流

列表路径固定为：`SQL 计数 → SQL 筛选/分页摘要 → 批量复核结果 → 批量执行状态 → AuditListResponse`。摘要表只保存列表已有响应所需的紧凑模型，不保存证据子图、完整时间线、高级推理或原始音频。新命令审计与摘要在同一事务写入；复核终态写入时，同一事务更新摘要的有效裁决。

链校验使用进程内缓存和数据库修订号：首次完整校验；仅发生追加写入时从上次尾部继续校验；更新或删除会增加非追加修订号并强制完整校验。同一仓储实例用条件变量保证单任务，等待者共享完成结果。散列发生在 SQLite 只读事务结束后，FastAPI 同步路由在线程池执行，不占用主事件循环。

前端审计页挂载时只请求列表。全局链校验必须由用户点击发起，进行中禁止重复点击。列表保留现有 AbortController、请求编号和旧数据保留机制。非裁决页面分别展示后端健康状态与“当前页面未启用实时通道”。

## 数据库调整

新增 `audit_list_summaries`，包含标识、排序/筛选字段、指令摘要、输入来源、说话位置/角色、紧凑语义帧、原始裁决、门控结果、对齐路径和记录哈希。新增决策/时间、动作/时间、目标/时间索引。

新增 `audit_chain_revision` 以及审计表 INSERT/UPDATE/DELETE 触发器。INSERT 只增加总修订号；UPDATE/DELETE 同时增加非追加修订号，以区分可增量追加和必须完整重算的变更。

## 异常与边界

- 空页保留总数并返回空 `items`。
- 回填在事务内执行，失败回滚；迁移脚本先做 SHA-256 一致的数据库备份，异常时自动恢复。
- 原始 `audit_records.record_json` 不删除、不重写，原哈希链不参与摘要迁移。
- 外部篡改旧记录会触发非追加修订并进行完整校验，不能被缓存掩盖。
- 单条详情、单条完整性校验和导出响应结构保持不变。

## 测试策略

- 对同一 110 条命令审计逐字段比较旧列表算法和新摘要算法，覆盖分页、PASS/REVIEW/BLOCK 和时间筛选。
- 通过禁止旧逐条方法并统计批量方法调用，验证查询次数不随页大小增长。
- 覆盖回填幂等、关键字段一致、空页、缓存命中、追加增量、外部篡改和并发单任务。
- 运行冻结契约、复核终态、详情/单条校验、前端测试、TypeScript 检查和生产构建。
