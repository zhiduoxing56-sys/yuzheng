# 中文语音识别模型替换设计说明

## 背景与目标

当前语音链路使用 `openai/whisper-base`，中文短指令识别效果不足。本次将主 ASR 替换为 `SenseVoiceSmall`，保持现有前端语音入口、后端可信语音处理链、语义解析和安全裁决接口不变。

成功标准：前端提交语音后直接展示 SenseVoice 转写结果；真实模型推理、模型元数据与置信信息可审计；空转写和模型异常明确失败；现有文本输入不受影响。

## 现状与约束

- 运行环境固定为 `D:\software\anaconda\envs\yuzheng311\python.exe`。
- 当前机器为 CPU 环境，无 CUDA。
- 音频已统一为 16 kHz 单声道，最长 15 秒。
- 当前 `WhisperASRService` 与 Transformers Whisper API 强绑定。
- 模型只从本地缓存加载，不能在请求处理中临时联网下载。
- 工作区存在其他未提交改动，本次仅修改 ASR 相关文件。

## 方案对比

### 方案一：SenseVoiceSmall

- 优点：中文能力更有针对性；约 234M 参数；非自回归，适合 CPU 和短指令；兼顾普通话与粤语。
- 缺点：需要新增 FunASR 依赖与适配器；需要清理语言、情绪和声音事件标签；置信度口径与 Whisper 不同。

### 方案二：Paraformer-large

- 优点：面向中文识别，可使用车控热词增强专业词汇。
- 缺点：模型和资源占用更大；首次替换的依赖与验证成本更高。

### 方案三：Whisper-small

- 优点：沿用现有适配器，修改量最小。
- 缺点：仍是通用多语言模型，中文改善不确定；CPU 延迟更高。

## 推荐方案

以 `iic/SenseVoiceSmall` 作为唯一运行主模型，保留 Whisper 代码和配置回滚能力，但运行时不做静默双模型回退。这样既改善中文识别，也避免模型异常时产生不可审计的结果。

## 详细设计

### 架构

保留现有 `音频输入 → 格式与频谱处理 → 声学可信处理 → ASR → 语义 → 证据与安全裁决 → 前端结果` 数据流，仅把 ASR 服务替换成配置驱动的 SenseVoice 适配器。

### 关键组件

- 新增 SenseVoice 本地适配器，进程内延迟加载并复用模型。
- 配置固定模型 ID、revision、来源、语言和最大输入范围。
- 将 SenseVoice 富文本标签清理成普通转写文本，同时保留真实模型名称和推理耗时。
- 服务装配根据配置选择适配器，使前端和上层流水线无需修改接口。

### 数据流与接口

前端继续上传现有 PCM WAV。后端向 SenseVoice 传入规范化波形和 `zh` 语言提示，将输出映射到现有 `TranscriptionResult`。前端继续读取原有 `asr_result.text`、模型名称和状态字段，无需新增操作步骤。

### 异常与边界处理

- 模型不在本地缓存、依赖缺失或加载失败：返回明确的 ASR 服务错误。
- 空白、静音或仅含模型标签的输出：按空转写处理，不进入车辆授权。
- 不在请求期间联网下载模型，不伪造置信度，不静默回退 Whisper。
- SenseVoice 未提供可与当前整句概率等价的置信度时，返回 `null` 并标明方法为空。

### 测试策略

- 单元测试覆盖模型加载、中文输出、富标签清理、空输出和异常映射。
- 回归测试覆盖现有可信语音流水线和前端响应合同。
- 使用真实中文车控录音执行 SenseVoice 推理，记录转写文本和 CPU 延迟。
- 运行相关后端测试，确认文本输入和安全裁决不受影响。

## 风险与待确认项

- 当前环境尚未安装 FunASR，且模型可能尚未缓存；安装依赖和下载权重需要联网授权。
- 是否优于 Whisper-base 最终以项目自己的中文车控录音结果为准，不以模型公开宣传代替本地验证。
