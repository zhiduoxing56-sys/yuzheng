# 知识库构建要求 v1

## 1. 目标

构建一个能够直接约束车辆控制指令的安全知识库。

知识节点必须能够明确表达：

1. 约束哪一条指令；
2. 需要读取哪些证据字段；
3. 证据值满足什么条件；
4. 条件成立或不成立时产生 `ALLOW`、`BLOCK` 或 `REVIEW`。

本次构建只允许使用项目已有冻结 YAML 中的语义和证据定义，坚决不扩展新的意图、动作、对象、区域、模式、证据类型或证据字段。

## 2. 冻结输入范围

知识库构建时只能使用以下六个文件：

1. `data/nlu/spec/intent_registry_unified_v1.yaml`
2. `证据/evidence_type_catalog_v1.yaml`
3. `证据/evidence_runtime_mapping_v1.yaml`
4. `证据/evidence_demand_registry_v1.yaml`
5. `config/safety_rules.yaml`
6. `证据/knowledge_constraint_contract_v1.yaml`

前五个现有 YAML 是只读冻结输入，知识库构建方不得修改。第六个文件是知识节点的结构合同。

除这六个文件外，其他代码、测试数据、Demo 场景、历史注册表和自然语言同义词均不得被用来创建新的正式值。

## 3. 不得扩展的内容

知识库不得新增或修改以下内容：

- `intent_id`
- `action`
- `target`
- `area`
- `mode`
- `direction`
- `control_attribute`
- intent `value` 的数据类型、单位和取值范围
- `evidence_type`
- evidence `field`
- evidence 字段的数据类型和单位
- 条件运算符
- 裁决效果

知识库只允许新增“现有指令 + 现有证据字段 + 具体条件 + 具体效果”的知识节点。

## 4. 知识节点输出格式

正式交付文件为：

```text
knowledge_constraints_v1.jsonl
```

每行必须是一个完整 JSON 对象，一行只表达一条约束。

每个节点必须包含以下内容：

```yaml
node_id: 知识.灯光.夜间关闭限制.001
node_type: 安全知识
title: 行驶且低照度时禁止关闭前照灯
source: GB 7258-2017
chapter: 第8章
clause: 8.2.1

command:
  intent_id: HEADLIGHT_SET_MODE
  action: SWITCH_MODE
  target: HEADLIGHT
  area: ANY
  mode: OFF

evidence:
  speed:
    type: VEHICLE_SPEED
    field: value
  light:
    type: ENVIRONMENT_CONDITIONS
    field: ambient_illumination

when:
  all:
    - field: speed
      op: GT
      value: 0
    - field: light
      op: LT
      value: 20

effect:
  then: BLOCK
  else: ALLOW
  reason_code: LOW_LIGHT_HEADLIGHT_OFF_PROHIBITED
  reason: 行驶且环境照度低于20 lux时禁止关闭前照灯
```

`ANY` 只是知识节点的通配符，表示该字段不参与匹配；它不是新的业务取值，不得写入运行时 `SemanticIntent` 或 Evidence value。

## 5. command 构建要求

### 5.1 允许字段

`command` 只允许：

```text
intent_id
action
target
area
mode
value
direction
control_attribute
```

`intent_id`、`action` 和 `target` 必填，其他字段只在需要缩小指令匹配范围时填写。

### 5.2 一致性要求

- `intent_id` 必须存在于统一语义注册表。
- 只允许 `runtime_identity: FORMAL` 的 intent。
- `action` 必须等于该 intent 的 `canonical_action`。
- `target` 必须等于该 intent 的 `canonical_target`。
- `area` 必须是 `ANY` 或该 intent `allowed_areas` 中的值。
- `mode` 必须是 `ANY` 或该 intent `mode_contract` 允许的值。
- `value` 必须是 `ANY` 或满足该 intent `value_contract`。
- `direction` 必须是 `ANY` 或该 intent `direction_contract` 允许的值。
- `control_attribute` 必须是 `ANY` 或与该 intent 的冻结值一致。

即使某个 action 或 target 存在于其他 intent，也不得与当前 `intent_id` 跨 intent 拼装。

## 6. evidence 构建要求

### 6.1 上下文的唯一表达方式

所有车速、挡位、天气、照度、车门、门锁、雨刷、权限、障碍物等上下文，都必须以下面的方式表达：

```yaml
别名:
  type: 标准 Evidence Type
  field: 该 Evidence Type 的正式字段
```

禁止在节点中另行创建 `vehicle_context`、`weather_context`、`scene` 或其他自由上下文字段。

### 6.2 类型和字段要求

- `type` 必须来自 `evidence_type_catalog_v1.yaml`。
- `field` 必须来自该 type 在 `evidence_runtime_mapping_v1.yaml` 中的 `value_schema`。
- 标量 Evidence 统一使用 `field: value`。
- 对象 Evidence 必须使用其已声明的内部字段。
- 节点不得改变证据字段的数据类型或单位。
- `when` 中使用的每一个别名都必须在 `evidence` 中声明。
- `evidence` 中没有被 `when` 使用的项应删除，禁止无用证据扩张。

## 7. when 构建要求

### 7.1 逻辑结构

`when` 必须且只能使用一种逻辑组：

```yaml
when:
  all: [...]
```

或：

```yaml
when:
  any: [...]
```

第一版不允许嵌套 `all/any`，不允许 `NOT`，不允许脚本表达式。

### 7.2 条件字段

每个条件只允许：

```yaml
field: evidence别名
op: 运算符
value: 比较值
```

### 7.3 运算符

| Evidence 字段类型 | 允许运算符 |
|---|---|
| number | `EQ NE GT GTE LT LTE` |
| string / enum | `EQ NE IN NOT_IN` |
| boolean | `EQ NE` |

`IN` 和 `NOT_IN` 的 `value` 必须是非空列表。

数值必须使用 Evidence Runtime Mapping 已声明的单位，知识节点不得进行隐式单位换算。

如果 Evidence Runtime Mapping 只将某字段定义为普通 `string`，且冻结文件中没有给出允许枚举，知识节点不得自创新枚举。只能使用冻结文件中已明确出现的值。

### 7.4 禁止内容

禁止：

```yaml
conditions: [高速行驶, 夜间]
```

禁止：

```yaml
when: "speed > 0 and light < 20"
```

禁止 Python、SQL、正则脚本、函数调用和自然语言判断。

## 8. effect 构建要求

`effect` 固定为：

```yaml
effect:
  then: BLOCK
  else: ALLOW
  reason_code: UPPERCASE_SNAKE_CASE
  reason: 中文原因
```

`then` 和 `else` 只允许：

```text
ALLOW
BLOCK
REVIEW
```

执行语义：

- `command` 不匹配：节点不适用，不产生效果。
- `command` 匹配且 `when` 成立：使用 `then`。
- `command` 匹配且 `when` 不成立：使用 `else`。
- 知识节点中需要的证据缺失、过期、被篡改、值不合法或关键冲突：不得进入 `else: ALLOW`，必须由现有证据安全机制按 fail-closed 处理。

`ALLOW` 只表示该知识约束没有阻断，不得覆盖权限检查、证据硬门或其他 `BLOCK`。

## 9. 多节点合并规则

多个节点同时适用时固定按以下优先级合并：

```text
BLOCK > REVIEW > ALLOW
```

- 任意适用节点产生 `BLOCK`，知识层结果为 `BLOCK`。
- 没有 `BLOCK` 但存在 `REVIEW`，结果为 `REVIEW`。
- 只有在不存在 `BLOCK/REVIEW` 时，`ALLOW` 才能继续进入现有裁决链。
- 没有节点匹配时，知识层不生成新结论，保持现有流程行为。
- 知识库不得通过相似度分数覆盖 `BLOCK`。

## 10. 与现有流程的兼容要求

为了与现有知识检索字段兼容，正式 JSONL 节点还应保留以下现有字段：

```yaml
semantic_description: 知识说明
canonical_action: HEADLIGHT_SET_MODE
conditions: []
required_evidence: [VEHICLE_SPEED, ENVIRONMENT_CONDITIONS]
optional_evidence: []
trust_level: L1
metadata:
  knowledge_id: SAFETY-HEADLIGHT_SET_MODE-00001
  constraint: ALLOW_WITH_CONDITION
```

这些兼容字段必须从结构化约束派生，不得独立填写出现两套含义：

- `canonical_action` 必须等于 `command.intent_id`。
- `required_evidence` 必须等于 `evidence` 中实际用于 `when` 的 type 去重集合。
- `conditions` 固定为空列表，不再用自然语言条件参与裁决。
- `metadata.constraint` 仅作为现有可信节点兼容标识，实际裁决以 `effect` 为准。

`vector` 可以为 `null` 或由现有向量化流程生成，知识库构建方不得为了改变裁决而手工编辑向量。

## 11. safety_rules 范围要求

`config/safety_rules.yaml` 仅用于确认当前已有规则不被知识库重构遗漏。

知识库不得修改 safety rule id，不得发明新的 evaluator。能以现有意图和证据字段表达的指令约束，应转为本规范的结构化知识节点。

证据缺失、篡改、过期、信任阈值、语义模型降级等系统级硬门保持现有机制，不要在每个知识节点中重复定义。

## 12. 强制验收条件

每个知识节点在进入正式库前必须同时通过以下检查：

1. JSON 结构可解析。
2. 不包含未知字段。
3. `node_id` 和 `metadata.knowledge_id` 全库唯一。
4. `intent_id` 存在且是 `FORMAL`。
5. action、target、area、mode、value、direction、control_attribute 与 intent 合同一致。
6. 所有 evidence type 存在于冻结 catalog。
7. 所有 evidence field 存在于对应 runtime mapping。
8. 条件 value 类型与 evidence field 类型一致。
9. 条件 op 适用于 evidence field 类型。
10. 所有 `when.field` 都引用已声明 evidence 别名。
11. `then/else` 只使用 `ALLOW/BLOCK/REVIEW`。
12. 兼容字段与结构化约束一致。
13. 没有修改或扩展任何冻结 YAML 值。
14. 每个节点至少通过一个 `then` 用例、一个 `else` 用例和一个 command 不匹配用例。

任意一项不通过，该节点不得进入正式知识库。不允许带警告发布，不允许自动修正未知值，不允许使用同义词猜测正式值。

## 13. 交付内容

知识库构建方只需交付：

1. `knowledge_constraints_v1.jsonl`：正式知识节点。
2. `knowledge_constraint_acceptance_v1.jsonl`：每个节点的 then、else、不匹配和边界用例。
3. `knowledge_constraint_validation_report_v1.json`：全部强制检查结果，必须为零错误。

## 14. 最终判定标准

一个合格的知识节点必须做到：

> 不阅读法规自然语言、不调用大模型、不创造新字段，只依靠节点中的 command、evidence、when 和 effect，即可唯一得出 ALLOW、BLOCK、REVIEW 或不适用。

只有满足该标准，知识节点才能真正参与指令约束。
