可以。你先把这套方案想成一句特别朴素的话：

**以前我们的安全门是“我写了一条规则，所以它可以拦车控”；现在这套方法要求“这条规则先证明自己有资格成为硬规则，然后它才能在运行时一票否决”。**

这就是整套方案最核心的变化。文档开头其实就在回答这个问题：“一条安全规则凭什么拥有执行前的一票否决权？”

我从头带你跑一遍，你把这一遍弄懂，后面所有公式基本都会自己对上。

### 1. 为什么还要搞这一套？直接写“行驶中禁止开门”不行吗？

技术上当然能写。

比如我们直接在代码里写：

```text
如果车速 > 0：
    禁止开门
```

它立刻就能工作。

问题出在评委追问：

“凭什么这么规定？”

你说安全。

他继续问：

“安全依据在哪？”

然后还有：

“什么状态叫行驶？”
“所有车型都这样吗？”
“有没有例外？”
“是谁把法规转成这条代码的？”
“大模型如果理解错法规怎么办？”
“新规则和旧规则冲突怎么办？”
“谁批准它拥有一票否决权？”

传统的硬编码规则很难完整回答这一串问题。你现在的方法就是给**硬安全规则自己建立一套准入制度**：来源、含义、适用范围、逻辑一致性、边界测试和人工审核全部闭合之后，它才能进入正式规则库。

所以你先记住：

> **这套技术的主要创新对象，其实是“安全规则本身”。**

它先解决“规则怎么变得可信”，然后才解决“可信规则怎么在线拦危险动作”。

---

### 2. 整套方案实际上只有两大阶段：造规则，和用规则

文档看起来十九节很多，脑子里其实只需要两块。

第一块叫**离线规则构建**。

你提前把法规、车辆安全分析等材料处理成经过审核的正式安全契约。

第二块叫**在线安全监视**。

汽车正在运行的时候，根据当前用户要求执行的动作和车辆状态，调用这些已经批准的安全契约进行判断。整个文件也是按照这个边界组织的。

你可以把它理解成：

```text
赛前/部署前：

法规、安全分析
        ↓
产生规则
        ↓
验证规则
        ↓
批准规则
        ↓
正式规则库


汽车运行时：

用户车控请求
        ↓
读取正式规则
        ↓
检查当前动作是否违反规则
        ↓
违反 → 阻断
没有违反 → 继续后面的因果风险判断
```

所以大模型也不会在用户说一句话以后临时读法规、临时编安全规则。运行时安全门使用的规则全是**提前构建、提前验证、提前批准、提前发布**的。

这点很重要。

## 3. 那这些安全规则究竟从哪来？

这里有三种来源，但地位不同。

第一种最容易理解：**正式法规和安全规范。**

例如某正式规范要求：

```text
车辆行驶 + 低照度
→ 前照灯应该保持开启
```

于是我们可以从这条规范中形成安全约束。大模型可以帮助把长篇自然语言抽出来，但大模型自己没有资格宣布：

> “我觉得晚上关灯危险，所以我创建一条硬规则。”

它只能当离线整理助手。每个条件、义务、禁止、例外最终都得能回到来源。

第二种来源特别重要：**车辆系统安全分析。**

因为现实里很多规则没有一句法规原文能和你完全对应。

比如：

> 行驶中不能通过语音打开左前车门。

你可能找不到一条法规恰好写着“车载语音助手不得在车辆运动时开启左前车门”。

那怎么办？

你从车辆控制过程分析：

```text
车辆正在运动
+
打开车门
↓
可能产生危险
↓
车辆运动状态下，不得授权车门开启
```

于是得到一条**工程安全约束**。

这类规则的可信来源就写：

> 车辆级系统危险分析。

而且可以一路追踪：

```text
危险
→ 不安全控制动作
→ 危险场景
→ 安全约束
```

文件就是这样定义工程安全规则来源的。

第三种来源是**事故案例和动态安全情报**。

这块特别容易理解错。

今天网上出现一个新事故，并不会：

```text
新事故
→ 自动生成硬规则
→ 明天直接阻断车辆
```

这样太危险。

正确路径是：

```text
事故
↓
发现一个可能的新风险
↓
候选风险
↓
重新进行正式安全分析
↓
候选安全约束
↓
验证审核
↓
才可能成为正式规则
```

所以事故的作用主要是**发现我们以前没想到的风险**。

这一点你可以记一句：

> **法规和正式安全分析可以产生规则，事故主要负责发现问题。**

# 4. 最核心的东西来了：什么叫“安全契约”？

这应该是整篇你最需要真正理解的概念。

你以前的规则可能长这样：

> 行驶中禁止开门。

现在我们不满足于一句话，我们把它变成机器能够执行的结构。

安全契约的核心形式是：

[
A_i(\mathbf s)
\Rightarrow
G_i(\mathbf s,a,\mathbf s^+)
]

别被公式吓到。

它就两个东西：

**前提条件 (A)**：

> 什么情况下这条规则生效？

**安全保证 (G)**：

> 在这种情况下，执行动作以后必须保持什么安全状态？

文件也是这么定义的。

比如前照灯。

我们先限定这条契约管的动作是：

```text
关闭前照灯
```

它的前提：

[
A=
车辆正在行驶
\land
当前处于低照度
]

它的安全保证：

[
G=
执行动作以后，前照灯必须保持开启
]

于是这条规则真正表达的是：

> **如果车辆正在行驶且当前低照度，那么针对“关闭前照灯”这个动作，执行后必须依然满足“前照灯开启”。**

这就比一句：

> 夜间禁止关灯

精确得多。

因为你已经明确了：

```text
管哪个动作
什么情况下生效
需要看哪些车辆事实
动作会产生什么结果
最后必须保持什么状态
```

# 5. 为什么还需要“动作模型”？

这也是整个方案里很漂亮的一步。

安全契约要求：

[
执行以后前照灯=开启
]

但现在用户说：

> 关闭前照灯。

安全门怎么知道“执行完以后会发生什么”？

所以我们有：

[
T_{\mathrm{act}}(\mathbf s,a)
]

你可以把它理解成一个很小的**动作效果表**。

比如：

```text
关闭前照灯
→ 前照灯状态 = OFF

打开左前车门
→ 左前车门状态 = OPEN

打开车窗
→ 对应车窗状态 = OPEN
```

它不需要跑一次真实车辆才知道结果。

因为对于这种离散车控，动作的直接效果是确定的。

所以收到：

> 关闭前照灯

之后，系统预测：

[
\widehat{\mathbf s}^{+}:
前照灯=OFF
]

而安全契约要求：

[
前照灯=ON
]

于是：

[
G=0
]

直接阻断。文件第九节就是在描述这个过程。

所以你可以理解：

> **动作模型负责回答“你如果真执行这个动作，会把相关车辆状态改成什么”。**

安全契约负责回答：

> **“改完以后这个状态能不能接受”。**

这俩合起来才形成真正的执行前预测。

# 6. 那什么叫“证明携带”？这个名字终于可以理解了

假设现在我们有一条候选规则：

[
R_i
]

比如：

> 低照度行驶时，关闭前照灯不得获得执行授权。

系统不会因为它看起来合理就直接放进安全门。

它还必须带着一个：

[
\Pi_i
]

也就是**安全保证包**。

所以正式对象是：

[
(R_i,\Pi_i)
]

这里“携带”的意思就出来了：

> **规则自己带着一整套说明“我为什么有资格成为硬规则”的材料。**

现在保证包已经收敛成四块。

可以把它理解成一条安全规则的“档案袋”。

里面有：

1. **来源追踪证据**：这条规则到底从哪里来的，原文在哪里，有没有被大模型改错含义。
2. **逻辑证明**：规则内部有没有矛盾，和现有规则有没有冲突。
3. **测试证据**：正常情况、危险情况、边界情况、例外情况都测过没有。
4. **审核证据**：最终谁批准、批准的是哪个版本。

比如我们已有：

```text
规则甲：
低照度行驶 → 前照灯必须开启

规则乙：
低照度行驶 → 前照灯必须关闭
```

这俩显然打架。

逻辑验证阶段就应该发现：

[
C\Rightarrow L=ON
]

同时：

[
C\Rightarrow L=OFF
]

在同一适用范围中冲突，所以不允许发布。文件专门拿这个例子说明规则冲突检测。

最终只有：

[
Verify(R_i,\Pi_i)=1
]

而且人工审核通过，规则才能进入：

[
\mathcal R_{\mathrm{released}}
]

也就是**正式已发布规则库**。

到这里“证明携带”的核心你应该已经能理解：

> **一条规则想获得“一票否决权”，得先把自己的来源、逻辑、测试和审核材料交出来接受验证。**

---

# 7. 大模型到底参与哪里？

这一点特别关键。

大模型参与**造候选规则**。

例如给它一份法规：

```text
原始法规
↓
大模型切分条款
↓
抽取适用主体
↓
抽取触发条件
↓
识别禁止/义务
↓
映射车控动作
↓
抽取例外
↓
绑定原文位置
```

最后输出类似：

```text
受控动作：关闭前照灯
触发条件：车辆行驶、低照度
义务：前照灯保持开启
来源：某法规第×条
```

但是大模型做到这里就停。

它没有：

```text
发布权限
修改正式规则权限
运行时临时增加规则权限
跳过安全门权限
```

文件把这个权限边界写得很死。

所以即使大模型幻觉了：

> “根据法规，停车时禁止开窗。”

这条候选规则还得经历来源回指、逻辑检查、测试和审核。

查不到来源或者审核不通过：

```text
候选规则
×
正式规则
```

它永远进不了安全门。

# 8. 在线运行的时候，整条链到底怎么跑？

这部分是你答辩最应该会讲的。

假设用户说：

> **把前照灯关了。**

前面的语义模块已经把它解析成规范动作：

```text
HEADLIGHT_SET_MODE = OFF
```

到了这套安全监视器以后，依次发生下面几步。

### 第一步：根据动作找规则

系统在正式规则库里找：

> 哪些正式安全契约管“关闭前照灯”？

得到：

[
\mathcal R_a
]

这里必须做**确定性匹配**，不能用向量相似度。

因为硬规则不能出现：

> “这个规则和关闭前照灯有 87% 相似，所以我猜它应该参与一票否决。”

文件明确禁止这样做。

然后再看车型、地区、配置、版本等静态范围。

最终得到：

[
\mathcal R_{\mathrm{match}}
]

意思是：

> **与当前动作和当前适用范围相匹配的正式规则。**

# 9. 为什么现在一定是“匹配规则 → 查证据 → 判断触发”？

这就是刚刚我们专门修掉的那个逻辑漏洞。

假设规则是：

[
车辆行驶\land低照度
\Rightarrow
前照灯保持开启
]

现在你刚找到这条规则。

你能不能直接说：

> 这条规则现在已经触发？

不能。

因为你还不知道：

```text
车是不是在行驶？
是不是低照度？
```

所以接下来先看这条规则声明的证据需求：

[
E_i^H=
{
车辆运动状态,
环境照度,
前照灯状态
}
]

然后看证据质量模块给安全门的：

[
E_{\mathrm{valid}}(t)
]

它代表：

> **当前已经通过质量评估、允许安全门使用的事实。**

文件明确把证据真实性、时效性、来源冲突、篡改等问题留给证据质量模块，安全契约模块只消费结果。

所以这里有一个非常清楚的职责分工：

```text
证据质量模块：
“现在车速这个数据可信吗？”

安全契约模块：
“如果可信车速表明车辆正在运动，
这个动作还能不能做？”
```

这两个千万别混。

---

# 10. 如果关键证据没有怎么办？

比如安全契约需要：

```text
车辆运动状态
环境照度
前照灯状态
```

结果证据质量模块只给了：

```text
车辆运动状态
前照灯状态
```

环境照度无效或者拿不到。

那么系统无法判断：

[
A_i=
车辆行驶\land低照度
]

究竟成立不成立。

所以这里采取失效闭锁：

[
E_i^H\nsubseteq E_{\mathrm{valid}}
\Rightarrow
高风险请求不执行
]

这不代表安全门宣布：

> “环境光传感器坏了。”

它只知道：

> **我需要一个有效环境照度事实，现在没有，所以我没有资格证明这个高风险动作能够跨过硬安全边界。**

这正是第十三节的含义。

---

# 11. 证据齐了以后才真正判断“规则有没有触发”

假设当前有效事实是：

```text
车辆速度 = 60 km/h
环境 = 低照度
前照灯 = ON
```

于是：

[
A_i(\mathbf s)
==============

车辆行驶\land低照度
=1
]

这时这条规则才真正进入：

[
\mathcal R_{\mathrm{triggered}}
]

也就是：

> **当前真的已经触发的规则集合。**

文件现在严格定义成：

[
\mathcal R_{\mathrm{triggered}}
===============================

{
R_i\in\mathcal R_{\mathrm{match}}
\mid
A_i(\mathbf s)=1
}
]



所以三个词你一定要分清：

```text
正式规则
↓
匹配规则
↓
触发规则
```

正式规则：

> 规则库里合法存在。

匹配规则：

> 它管当前这个动作、车型、版本。

触发规则：

> 当前车辆状态真的满足它的危险前提。

这一改以后逻辑就完全顺了。

---

# 12. 最后怎么决定阻断？

继续刚才的例子。

当前：

```text
车辆行驶
低照度
```

所以规则被触发。

用户要：

```text
关闭前照灯
```

动作模型预测：

```text
执行后：
前照灯 = OFF
```

安全契约要求：

```text
执行后：
前照灯 = ON
```

所以：

[
G_i=0
]

于是：

[
BLOCK
]

整个在线过程就是：

```text
关闭前照灯
↓
找到相关正式契约
↓
适用范围匹配
↓
证据齐全
↓
车辆行驶 + 低照度
↓
规则触发
↓
预测执行后前照灯关闭
↓
违反“前照灯必须保持开启”
↓
阻断
```

这就是安全门真正做的事。

# 13. 再换一个场景，你会发现这种方法比黑名单强很多

还是：

> 关闭前照灯。

假设当前：

```text
车辆驻车
白天
```

第一步仍然匹配到前照灯规则。

证据也都齐。

但：

[
A_i(\mathbf s)=0
]

因为“车辆行驶＋低照度”不成立。

所以这条规则根本不会进入触发集合。

也就不会靠这条硬规则阻断。

这说明系统没有一个简单黑名单：

```text
关闭前照灯 = 永远禁止
```

它实际表达的是：

```text
关闭前照灯
+
当前车辆状态
+
正式安全约束
→
决定当前是否禁止
```

这也是安全契约比动作黑名单更强的核心原因。文件第九节专门强调同一个动作在不同状态下可以得到不同判定。

# 14. 那“行驶中打开车门”也是完全一样

你可以自己套公式。

动作：

[
a=打开左前车门
]

规则前提：

[
A=
车辆正在运动
]

安全保证可以表达为：

[
G=
执行后左前车门不得进入开启状态
]

动作模型：

```text
打开左前车门
→
左前车门 = OPEN
```

当前：

```text
车速 = 50 km/h
```

所以：

[
A=1
]

动作预测：

[
s^+:
车门=OPEN
]

安全保证要求：

[
车门\neq OPEN
]

于是：

[
G=0
]

安全门阻断。

如果车辆已经驻车：

[
A=0
]

这条规则就不触发。

你现在应该能看到一个特别清楚的规律：

> **我们拦的从来不是“打开车门”这个动作本身，我们拦的是“在满足某种危险前提时，执行这个动作会破坏已经正式发布的安全保证”。**

# 15. 那因果贝叶斯还干嘛？安全契约都这么强了

这个边界也必须搞懂。

安全契约特别擅长：

```text
条件明确
动作明确
安全边界明确
结果可以确定判断
```

比如：

```text
车辆运动 → 禁止开门
低照度行驶 → 前照灯必须开启
```

这种规则可以给很强的确定性判断。

但是现实中的风险还有大量这种：

```text
车速比较快
+
附近车辆距离比较近
+
道路湿滑
+
驾驶员当前操作
+
环境复杂
↓
风险可能升高
```

这里很难形成：

```text
A → G
```

这种绝对刚性的硬契约。

所以这些复杂、多因素、概率性的风险继续交给因果贝叶斯。文件也明确把两者分成“确定安全保证的风险空间”和“复杂概率风险空间”。

因此整条系统关系是：

```text
硬安全契约
↓
有没有违反绝对不能碰的边界？
│
├─ 有 → 直接阻断
│
└─ 没有
    ↓
因果贝叶斯
    ↓
复杂风险判断
    ↓
后续综合裁决
```

而且有一条铁律：

```text
硬安全契约已经判定违反
↓
后面的因果概率再高
↓
也不能恢复执行
```

文件明确规定硬安全层拥有最高否决权。

这个设计非常合理。

因为假设：

```text
法规硬约束：这个动作禁止
因果模型：我算出来安全概率 99%
```

你不能说：

> 那 99% 很高，还是执行吧。

不行。

硬边界已经触发，后面没有恢复权限。

---

# 16. 最后你一定要理解：这套东西究竟“保证”了什么

它不能保证：

> 通过安全门 = 现实世界绝对不会出事故。

这句话绝对不能说。

它真正保证的是：

在正式规则正确加载、证据已经通过质量评估、动作模型适用于当前动作等前提下，如果一个动作通过硬安全监视器，那么：

[
\forall R_i\in\mathcal R_{\mathrm{triggered}},
\quad
G_i=1
]

翻译成人话：

> **这个动作没有违反当前已经正式发布、并且当前条件下真正触发的任何硬安全契约。**

文档第十六节就是专门限制这个保证边界的。

未知风险怎么办？

继续由：

```text
因果风险层
+
其他后续安全机制
```

处理。

所以这套方法最准确的一句话，我建议你脑子里以后始终记成：

> **先让每条硬安全规则证明自己有资格“硬”，再让这些正式规则在运行时根据当前动作和车辆事实判断是否触发；一旦动作将破坏某条已触发规则要求维持的安全状态，就在执行前直接阻断。复杂而无法形成确定规则的风险继续交给因果贝叶斯。**

你只要真正理解这句话，十九节其实都已经串起来了。
