我查了一圈之后，反而更确定你这个担心是对的。当前版本真正薄弱的地方就在“硬规则为什么有资格成为硬规则”。现在的五条件资格函数把来源权威性、结论确定性、可观测性、形式可执行性和不可补偿性列出来了，逻辑方向没问题，但它依然属于“资格判断”，没有形成一条可以审计、验证、复现的证明链。 换句话说，现在能够回答“我们觉得什么样的规则应该进入硬门”，还很难回答评委一句更狠的问题：“你凭什么证明数据库里的这一条真的有资格拥有一票否决权？”

我更推荐把这一块整体升级成一个新的方法：**基于证明携带安全契约的运行时安全保障机制**。这个方案不用凭空造理论，它可以把系统理论安全分析、法律规则机器化、来源追踪、安全契约、结构化安全论证、形式验证、证明携带思想和运行时安全保障几个已经非常成熟的方向组合起来，再专门针对“自然语言车控指令进入车辆执行域”做适配。这样专业背书会强很多。

当前方案里的

[
\mathcal K_{\mathrm{trusted}}
\rightarrow
\operatorname{HardEligible}
\rightarrow
\mathcal K_{\mathrm{hard}}
]

我建议直接废掉“满足五个布尔条件就晋升”的思路，改成：

[
\boxed{
\text{候选安全约束}
\rightarrow
\text{安全契约}
\rightarrow
\text{证明包生成}
\rightarrow
\text{形式核验}
\rightarrow
\text{安全论证审核}
\rightarrow
\text{签名发布}
\rightarrow
\text{运行时安全门}
}
]

核心变化非常大：**一条规则能不能进入硬门，由它是否具有完整、可校验的安全证明包决定。**

你可以把它理解成“规则自己带着身份证、出生证明、适用范围、需要什么证据、为什么必须拦、形式验证结果和审核签名一起上车”。这个思想可以借鉴经典的“证明携带代码”：原始思想要求待执行代码附带一个能够被接收方快速验证的安全证明，接收方无需相信代码生产者，只需验证证明是否满足预先定义的安全策略。([数字对象标识符][1]) 我们把这个思想从“代码携带证明”迁移到“安全规则携带证明”，这里才有很好的方法创新空间。

### 一、先解决最根本的问题：硬规则究竟从哪里来

这里不能再笼统写“法规、标准、事故案例、安全知识”。这些东西的法律和工程地位完全不同。

我建议把来源严格拆成三个层级。

第一类是**规范性硬约束源**。中国部署版本直接从国家法律法规数据库、国务院和主管部门正式法规、国家标准全文公开系统中的现行强制性国家标准取得。国家法律法规数据库本身就是正式法律法规来源；国家标准全文公开系统明确维护现行强制性国家标准。([全国人民代表大会][2]) 例如《道路交通安全法实施条例》第五十八条明确规定低照度、低能见度行驶情况下的灯光要求，这类条文本身就可以产生规范性约束。([政府网][3]) 当前生效的汽车整车信息安全强制性国家标准也可以进入安全治理来源库。([国家标准全文公开系统][4]) 国际车型再根据适用市场引入联合国车辆法规，例如联合国第十一号法规覆盖车门锁止与保持部件，第四十八号法规覆盖灯光及光信号装置安装。([联合国欧洲经济委员会][5])

第二类非常重要，叫**工程安全约束源**。很多你们真正想拦的危险车控，并没有法律条文直接写成“车辆速度大于某值时语音系统禁止打开某个车门”。如果硬说来自法律，很容易被专家抓住。这里应该使用汽车安全工程方法生成约束。系统理论过程分析特别适合这个问题：它首先建立系统控制结构，再识别“不安全控制动作”，然后从危险场景中导出安全要求和安全约束。麻省理工学院的官方方法手册明确包含“识别不安全控制动作—构造场景—形成要求和约束”这条链路。([MIT PSASS][6])

这一下你们很多规则的来源就变得非常专业。例如：

用户控制器
↓
语义车控请求
↓
车控执行接口
↓
车门执行器
↓
车辆物理状态

做系统理论过程分析时发现：

[
\text{控制动作}=\text{打开左前车门}
]

在

[
\text{车辆处于运动状态}
]

下属于不安全控制动作，于是导出：

[
\boxed{
车辆处于运动状态
\Rightarrow
不得向车门执行器发送开启控制
}
]

这条约束的来源就写成：

> 系统危险分析产生的车辆级安全约束

而无需假装某部法律逐字写了这句话。

这比现在“我们根据经验认为行驶中开门危险，所以写一个规则”强了好几个层级。

第三类是**事故和动态情报源**。这一层绝对不能自动产生硬规则。事故案例适合做危险发现、因果分析和规则缺口发现。麻省理工学院的事故分析方法本身就强调通过事故分析控制结构和因果因素来形成可操作改进。([MIT PSASS][6]) 所以每天新增的事故完全可以让智能体自动抓取、聚类、提取风险模式，但输出只能进入：

[
\mathcal K_{\mathrm{candidate}}
]

或者因果贝叶斯知识库。

它不能直接进入：

[
\mathcal K_{\mathrm{hard}}.
]

这样你之前一直纠结的“每天新事故怎么自动更新硬规则”也解决了：**事故更新安全认知，正式硬规则需要再次经过危险分析、工程确认和证明发布流程。**

### 二、规则数据库怎么真正建立起来

这里我反而不建议搞“一个关系数据库＋一个知识图谱数据库＋一个向量库＋一个规则库”四套事实源，那样很容易越做越乱。

最好只保留一个正式安全规则数据库作为唯一事实源，原始文件单独作为不可变附件保存。向量索引只能作为搜索加速器。

正式数据库可以围绕一个唯一对象：

[
\boxed{\text{安全契约}}
]

设计。

每条安全契约记录：

[
R_i=
\langle
来源,,
原文定位,,
规范类型,,
适用范围,,
危险编号,,
前置假设,,
受控动作,,
安全保证,,
证据依赖,,
动作模型,,
例外,,
版本,,
验证结果,,
审核状态,,
证明摘要
\rangle .
]

法律文本的机器表示可以直接借鉴法律规则标记规范的思想。这个国际标准专门区分义务、禁止、许可、法律来源、适用状态等规范语义，同时明确“法律规则是法律规范的形式表示”。([OASIS开放文档][7]) 所以大模型离线解析法律条款时，不要让它自由总结，强制它只输出：

[
\text{适用主体}
+
\text{条件}
+
\text{义务/禁止}
+
\text{受约束动作或状态}
+
\text{例外}
+
\text{生效范围}
+
\text{原文证据跨度}.
]

与此同时，每个字段必须反向链接到原始材料中的具体段落。来源关系可以借鉴万维网联盟的来源追踪模型，它就是用实体、活动和主体之间的关系保存“某个结果怎样产生、由谁产生、来源是什么”。([W3C][8])

于是数据库中的一条规则不会只长这样：

```text
夜间行驶不能关闭前照灯
```

它应该拥有类似这样的完整链：

```text
规则编号：灯光-0042

来源类型：
现行行政法规

来源：
道路交通安全法实施条例

条款：
第五十八条

原文位置：
……

规范类型：
义务

适用域：
中国道路车辆

触发条件：
车辆处于行驶状态
且低照度或低能见度

安全保证：
前照灯执行后必须保持开启

受控动作：
关闭前照灯

证据需求：
车辆运动状态
环境照度/能见度
当前前照灯状态

例外：
……

来源版本：
……

形式验证：
通过

审核状态：
已批准

发布签名：
……
```

这里最大的好处是：**数据库中已经不存在“孤零零的一条规则”。每条规则都是一份完整安全资产。**

另外，车辆信号名称不要继续自己拍脑袋扩展。车辆信号可以参考车辆信号规范，它的目标本身就是建立与具体协议无关的统一车辆信号语义；你们国内工程层又可以同时参考今年已经实施的《智能网联汽车 车控操作系统技术要求及试验方法》。([GitHub][9]) 这样“车辆速度、车门状态、灯光状态、挡位”等证据字段就有行业语义依据。

### 三、最关键的一步：怎么证明“它真的有资格当硬规则”

这里我建议引入一个新的核心对象：

[
\boxed{\Pi_i=\text{规则 }R_i\text{ 的安全证明包}}
]

只有

[
\operatorname{Verify}(\Pi_i)=1
]

时，规则才允许进入在线安全门。

这个证明包至少要证明六件事情：

[
\Pi_i
=====

{
\pi_{\mathrm{source}},
\pi_{\mathrm{sem}},
\pi_{\mathrm{scope}},
\pi_{\mathrm{obs}},
\pi_{\mathrm{logic}},
\pi_{\mathrm{test}}
}.
]

第一份证明说明来源合法且当前有效；第二份证明说明机器规则中的条件、禁止、义务、例外都能够逐项回指原文或者安全分析结果；第三份证明说明车型、地区、版本、功能范围已经闭合；第四份证明说明规则判断需要的物理量在当前车辆配置中真实可取得；第五份证明说明规则和已经生效规则没有逻辑冲突；第六份证明说明正例、反例和边界场景全部通过。

对于数据结构完整性，可以采用图约束验证语言，它能够声明数据必须满足的结构、基数、类型和逻辑条件，并产生机器可读验证报告。([W3C][10]) 对规则逻辑冲突，可以把条件编译成逻辑约束交给可满足性模理论求解器检查；这一类求解器的核心能力就是判断逻辑公式是否可满足。([Microsoft GitHub][11])

例如现有数据库中有：

[
C\Rightarrow L=\mathrm{ON}
]

新规则准备发布：

[
C\Rightarrow L=\mathrm{OFF}.
]

求解器发现同一适用域、同一条件下要求两个互斥状态，发布立即失败。

更重要的是，再把安全论证加进来。结构化安全论证已经有正式的国际元模型规范，可以用“主张—论据—证据”组织为什么一个安全要求成立。([OMG][12]) 汽车人工智能安全规范也明确强调安全相关属性应该能够支撑有说服力的安全保障主张。([ISO][13])

所以一条硬规则最终可以形成：

[
\boxed{
\text{主张：该规则具有不可补偿安全约束资格}
}
]

下面挂：

[
\text{权威来源证据}
]

[
+
\text{危险分析证据}
]

[
+
\text{形式化一致性证据}
]

[
+
\text{可观测性证据}
]

[
+
\text{仿真/测试证据}
]

[
+
\text{人工批准}.
]

这样“硬”终于有实质含义了。

### 四、我会把现在的“硬规则”改成“安全契约”

这一点也很重要。

一条车控硬安全约束最好统一写成：

[
\boxed{
A_i(\mathbf s)
\Rightarrow
G_i(\mathbf s,a,\mathbf s^{+})
}
]

其中 (A_i) 是该契约成立需要满足的前提，(G_i) 是动作执行以后系统必须保证的安全性质。

这种“假设—保证”契约是成熟的安全工程思想，现有研究已经用它来组织安全要求、模块化验证，以及运行阶段的动态安全保障。([科学直通车][14])

例如：

[
A:
\text{车辆运动}
\land
\text{低照度}
]

[
G:
\text{执行后前照灯状态}=\mathrm{ON}.
]

语音系统给出：

[
a=\text{关闭前照灯}.
]

动作模型得到：

[
\mathbf s^{+}:
\text{前照灯}=\mathrm{OFF}.
]

因此：

[
G(\mathbf s,a,\mathbf s^{+})=0
]

安全契约违反，立即拒绝。

这比当前五个资格条件好解释得多，因为评委问“为什么这是硬规则”，你可以一路从：

> 哪个危险 → 哪个正式约束 → 哪个安全契约 → 哪些车辆事实 → 哪个执行后状态 → 为什么违反

完整倒推回去。

### 五、还可以再先进一步：不要所有车控都只检查一个“执行后瞬时状态”

当前上传版使用

[
\widehat{\mathbf s}^{+}
=======================

T_{\mathrm{act}}(\mathbf s,a)
]

处理灯光和车门很漂亮。

但它对于“加速”“减速”“自动泊车”这种连续动作确实太简单。

我建议规则编译器根据车控类型产生三类安全监视器。

离散状态类，例如车门、车窗、灯光、屏幕，直接验证执行后状态不变量。

时序类，例如“某状态出现后一段时间内必须保持某控制状态”，编译成时序约束，由运行时监视器检查。

动力学类，例如加速、制动、未来如果扩展到横向控制，编译成安全状态集合或可达状态约束。控制屏障函数就是目前安全关键控制里用于验证和强制安全集合不变性的成熟方法。([arXiv][15])

这样你们的方法从：

[
\text{规则表}
]

升级成：

[
\boxed{
\text{法规/安全约束}
\rightarrow
\text{安全契约}
\rightarrow
\text{面向动作类型自动编译安全监视器}
}
]

这个技术层次就明显更高了。

### 六、运行时应该借“运行时安全保障”思想重新定义

这一块也能获得非常强的专业背书。

运行时安全保障研究的核心思想就是允许复杂、难以完全验证的智能模块负责性能和智能行为，同时在外部设置可验证安全监视器，在动作真正影响物理系统之前过滤危险控制输出。([arXiv][16]) 二〇二六年甚至已经出现针对高级自动驾驶指令的运行时保障研究：在高层命令执行前预测后续状态，并拒绝预计会进入不可接受区域的命令。([arXiv][17])

这和你们的场景其实特别匹配。

你们可以把系统重新抽象成：

[
\boxed{
\text{大模型/语义模块}
\rightarrow
\text{候选规范车控动作}
\rightarrow
\text{可验证运行时安全监视器}
\rightarrow
\text{授权}
\rightarrow
\text{执行接口}
}
]

其中智能模型有权提出动作，没有权决定安全规则。

而且二〇二六年的最新研究正在探索智能模块和可验证安全监视器之间更紧密的协同，同时明确要求这种协同必须满足形式条件，才能保留安全保证。([arXiv][18]) 这也给你们“因果贝叶斯＋确定性安全门”的协同提供了一个非常好的前沿背景。

### 七、这样以后，因果贝叶斯的位置也突然变得合理了

以前最大的问题是安全门和因果贝叶斯很像两套风险判断。

按现在的新设计：

[
\boxed{
\text{安全契约}
===========

\text{能够被证明的安全边界}
}
]

[
\boxed{
\text{因果贝叶斯}
============

\text{无法形成确定契约的复杂风险空间}
}
]

二者分界非常自然。

法规直接要求、系统危险分析确定、安全变量可观测、动作结果可验证的条件进入安全契约。

事故经验、复杂环境耦合、连续风险、多因素概率影响进入因果网络。

因此甚至不用再人为问：

> “这一条到底应该安全门判断还是因果贝叶斯判断？”

规则发布流程自己就回答了。

如果一个候选风险无法生成完整证明包：

[
\operatorname{Verify}(\Pi_i)=0,
]

它就不能拥有硬否决权。

它继续留在可信知识层和因果风险层。

这正是现在 `HardEligible` 缺失的那个机制。

### 八、所以我现在会彻底换掉原来关键技术的中心

如果按我现在查完这些资料之后重新定，我不会再把核心创新叫“可验证硬规则安全门”。

我更推荐：

> **面向智能车控的证明携带安全契约构建与运行时保障方法**

它的完整技术主线就是：

[
\boxed{
\begin{aligned}
&\text{法律法规/强制标准}
\
&+\text{系统危险分析}
\
&+\text{事故驱动危险发现}
\
&\downarrow
\
&\text{规范命题与安全约束}
\
&\downarrow
\
&\text{安全契约构建}
\
&\downarrow
\
&\text{来源证明+语义证明+可观测证明+一致性证明+测试证明}
\
&\downarrow
\
&\text{结构化安全论证}
\
&\downarrow
\
&\text{签名安全契约快照}
\
&\downarrow
\
&\text{运行时确定性安全监视器}
\
&\downarrow
\
&\text{执行前安全否决}
\end{aligned}}
]
